# 教学设计审查：《React 从零到专家》（2026-10-05）

审查范围：课程结构、学习目标、认知负荷、学习科学机制的落实程度、学习者定位与动机设计，以及与同类资源的比较。不重复技术审查（README.md、expert-summary.md）已覆盖的 API 正确性问题。

审查方法：
- 通读 `lessons-6-order.js`（37 课、5 阶段）与 `app.js` 全部机制代码（热身、间隔复习、预测、提示阶梯、自我解释、阶段测验）。
- 用脚本统计全部 37 课的时长、目标数、正文字数、示例数、预测题数、测验题数、练习与阶段测验专用题。
- 细读 16 课：阶段 1 的 1、4、7、9；阶段 2 的 14、16、17、18；阶段 3 的 19、21、24；阶段 4 的 25、26、29、30、31；阶段 5 的 35、37。通读全部 102 道课内测验、49 道阶段测验专用题和 32 道练习的任务、提示与检查代码。
- 用 Playwright 在构建版本上实际走了一遍预测、测验重答、提示阶梯、自我解释、阶段测验和复习页的流程，核对代码推断。

## 1. 总评与评分

**总分：6.5 / 10。** 这是一套在“内容选择”和“动手练习”上明显优于一般中文教程的课程，机制设计的野心也很大。但多项学习科学机制在实现上停留在“有这个环节”，而没有达到“环节真的起作用”的程度：预测题的答案常常写在代码注释里；测验的掌握标准是“看过正确答案后再答一次”；提示阶梯三次空点击就能拿到参考答案；自我解释没有任何反馈。学习者定位（需要什么 JS 基础）全课程没有任何说明，而总时长 11.1 小时与“专家”之间的差距也没有向学习者交代。

## 2. 主要优点

1. **课程脊柱是心智模型，不是 API 清单。** 第 4 课“一次渲染 = 一张快照”、第 19 课“状态跟着位置走”、第 21 课“每次渲染都有自己的 props、state 和函数”、第 30 课用 20 行实现 useState 解释“Hook 为什么依赖调用顺序”并回扣第 19 课。这些是 react.dev 上最难的几个“深入探讨”，课程用可运行示例把它们串成一条线（lessons-1.js 第 4 课；lessons-3.js `rendering`、`closures`；lessons-4.js `mini-react`）。

2. **练习检查“像用户一样操作”，并给出诊断性的失败信息。** 第 17 课检查程序先搜“张”，再快速输入“李”→“李四”，专门验证竞态（lessons-2.js `project-search` 的 test）；第 18 课同时检查界面行为和 reducer 的纯度（`s3 !== s0 && s0.cards[1].col === 'todo'`）；第 34 课检查 `stats.calls` 确认缓存真的生效。失败信息直接指向概念（“过期请求的结果覆盖了新结果（需求 7）”），这是形成性反馈的正确做法。

3. **第 35 课的练习是全课最好的设计。** 学习者写测试，检查程序把同一套测试跑在正确版本和两个有 bug 的版本上，要求“正确版本全过、bug 版本至少一个失败”（lessons-6-ex-testing.js）。这直接考察了“测试能不能发现 bug”这个目标本身，而不是考察“写没写 getByRole”。

4. **阶段测验的交错与迁移设计是真的。** 每次 10 题，5 题来自课内、5 题是只在阶段测验出现的读代码题（app.js:801–806；lessons-6-checks.js 共 49 题），题目跨本阶段所有课随机抽取，答错的题进入复习队列并链接回所属课（app.js:812–824）。阶段测验专用题质量普遍高于课内题：第 9 课 CHECK2“删除后用 `todos.length + 1` 生成 id 导致两条一起切换”、第 23 课 CHECK2“用 startTransition 包受控输入框”、第 33 课 CHECK2“`'2' + 1` 得到 `?page=21`”，都是在新代码上应用概念。

5. **间隔复习与课前热身实现扎实。** Leitner 五盒（1/3/7/16/35 天，app.js:537），只有第一次作答计入复习安排（app.js:573），热身优先抽到期题再抽上一课的题（app.js:640–644），每天最多 20 题。首页和侧栏都有到期数量提醒。这套机制在同类交互式课程里很少见。

6. **实战项目的“需求说明 + 实现约定”形式接近真实工作。** 第 9、17 课给出编号需求表和 id/类名约定；第 18 课把界面写好、只让学习者写 reducer，并解释“真实团队经常这样分工”。先设计 state 再写界面的引导（第 9 课“动手前先设计”）是好的元认知示范。

7. **文字简明，术语统一。** 一句一事、编号步骤、“一个概念只用一个说法”的术语表并在每课首次出现处加释义（app.js:671–690），对中文读者降低了阅读负荷。“打个比方”“常见坑”“深入一点”三类标注把主线和扩展分开，便于分层阅读。

## 3. 问题清单（按严重度排序）

### 高

**H1. 预测题的答案常写在被预测的代码注释或前文里，预测退化为“看注释选答案”。**
- 证据：
  - 第 4 课“快照 vs 函数式更新”的预测题问“点一次 +3（错误写法）后 count 是几”，代码注释逐行写着 `// count 是 0 → 请求设为 1`、`// count 仍是 0 → 请求设为 1`（lessons-1.js，`state` 课的 play 块），前一段正文已说“调用 setCount 不会立刻改变本次渲染中的 count”。
  - 第 14 课预测“打一个字会输出哪些 effect”，三个 `console.log` 的文字分别是 `'① 每次渲染后都执行'`、`'② 只在挂载时执行一次'`、`'③ count 变了'`。
  - 第 21 课“计数器卡在 1”的预测题，代码注释写 `// ❌ 这个回调创建于第一次渲染，它看到的 count 永远是 0`，JSX 里直接写 `{count}（永远停在 1）`。
  - 第 7 课预测题前一句是“下面的例子展示了用 index 当 key 的问题”，代码里标着 `❌ key=index` / `✅ key=id`。
  - 第 16 课 Portal 冒泡预测题的前一段正文：“事件也按 React 树冒泡”。
  - 引擎只隐藏了 `note`（app.js:319–321），没有隐藏代码注释和前文。
- 为什么影响学习：生成效应的前提是学习者必须自己产出答案并经历预测错误。答案可见时，这一步变成识别任务，预测正确率虚高，认知冲突不发生，“猜错后记得最牢”的说明（app.js:360）落空。
- 改法：为带预测的示例提供两份源码，预测前展示去掉解释性注释与 ❌/✅ 标记的版本，验证后再切换到带注释的版本；把剧透句移到预测块之后；在 `PREDICTIONS` 里加一个 `spoilerFree` 源码字段，或让引擎在预测前用正则剥掉含“→”“永远”“❌”“✅”“①②③”的注释行。

**H2. “掌握”的标准实际上是“被告知正确答案后再选一次”。**
- 证据：课内测验答错时显示“不太对，正确答案是 C”（app.js:521），随即提供“读懂解析后，再答一次”按钮（app.js:523–526）；`quizPassed` 只看最终选择是否等于答案（app.js:581–584）；课程完成 = 全部测验最终答对 + 练习通过（app.js:588）。Playwright 实测：答错 → 看到字母 → 重答 → 通过。
- 为什么影响学习：这是最弱的一种“掌握学习”。它把“完成”标记建立在识别记忆上，而不是检索。学习者会得到虚假的掌握信号，热身和复习队列记录的是第一次作答（这是对的），但课程完成状态与复习数据之间就出现了矛盾：一课“已掌握”，而它的题在复习队列里全部处于盒 0。
- 改法：（a）答错后只显示解析、不显示正确选项字母，重答时打乱选项；（b）重答答对不算“通过”，要求在下一次热身或复习中答对同一题才解锁完成；或（c）每题准备 2–3 个等价变体（改数字、改变量名），重答时换变体。最低限度：把“本课已掌握”改成“本课已完成”，把“掌握”留给阶段测验。

**H3. 提示阶梯可被零成本刷开，“半成品示例”是机械隔行挖空，不是渐隐示例。**
- 证据：
  - 解锁条件只看失败次数 `p.fails`（app.js:449–456），任何检查失败都计数，包括启动代码原封不动或语法错误。Playwright 实测：对未修改的起始代码连点三次“检查答案”，提示、半成品、参考答案全部解锁。
  - `fadedExample` 对参考答案中不在起始代码里的行按 `k++ % 2` 交替挖空（app.js:420–428）。实际产出：第 14 课挖掉了 `useEffect(() => {` 和 `return () => clearInterval(id);`，却保留了核心行 `setInterval(() => setSeconds(s => s + 1), 1000)`；第 21 课只有一行新代码，挖掉后等于什么都不给；第 9 课挖掉的包括 `</label>`、`</li>` 等闭合标签，并在 JSX 文本位置插入 `/* ✏️ */`，产出的是语法上无效的片段。
- 为什么影响学习：渐隐（faded worked examples）的研究支持的是“按解题步骤从后往前逐步去掉”，让学习者先补最后一步、再补最后两步。隔行挖空既不对应步骤，也常常把最难的一行留下、把样板行挖掉，无法起到搭脚手架的作用。而阶梯可刷开意味着“有益困难”完全依赖学习者自觉。
- 改法：（a）解锁条件加入“代码与起始代码有实质差异”或“距上次检查 ≥ N 分钟”；（b）为每道练习手写 2–3 级渐隐版本（`solutionFaded: [完整骨架+最后一步空, 最后两步空, …]`），用 `/* 第 N 步 */` 标记而不是插在 JSX 文本里；（c）提示文本按“方向 → 具体 API → 关键一行”三级手写，现在的 `hint` 只有一级。

**H4. 自我解释环节没有任何反馈，写一个字就能过；用来对照的“要点”大多不可观察。**
- 证据：`makeSelfExplain` 只保存文本（app.js:657–658），`p.note` 非空即显示自查清单，没有最小长度、没有关键词对照、没有示例答案；自查清单就是课程目标（app.js:662），而 116 条目标中 44 条以“理解 / 知道 / 了解 / 体会”开头（例如第 14 课“理解什么是副作用”，第 30 课“了解 Fiber 架构的核心思想”，第 18 课“体会界面与逻辑分离的好处”）。Playwright 实测输入 `x` 即可展开清单。导航栏把“有非空 note”显示为 ✓（app.js:716）。
- 为什么影响学习：自我解释的效果来自“发现自己讲不清”的那一刻。没有参照答案，学习者无法判断自己讲得对不对；对照“理解……”这类条目只会得到“我觉得我理解了”的错觉。这是全课程六个机制里形式化最严重的一个。
- 改法：（a）每课提供一段 3 句的“参考讲法”，写完后并排显示，并给出 3 个“你的总结里应该提到”的关键词清单（例如 useEffect 课：同步 / 依赖数组由代码决定 / 清理函数何时运行）让学习者勾选；（b）要求至少 40 个字才可展开；（c）把目标改写成可观察的动作（“能说出为什么 `[]` 不等于只执行一次”），自查才有意义。

**H5. 目标学习者和起点假设全课程没有交代；“11.1 小时从零到专家”在首页并列出现。**
- 证据：全部源码中搜不到“JavaScript 基础 / ES6 / 前提 / 需要会”等任何先修说明。第 1 课直接使用 `document.querySelector`、箭头函数、`addEventListener`；第 2 课出现展开运算符、三元表达式；第 4 课要求理解闭包式的“快照”。首页统计“11.1 小时学习时长”（app.js:865）与标题“一路学到 React 专家”（app.js:849）并排。阶段 5 的“毕业设计”要求 Next.js 全栈、Prisma、Auth.js、部署，而课内没有任何可运行的 Next.js 练习。
- 为什么影响学习：没有 JS 基础的学习者会在第 2–4 课以为是自己不行；有基础的学习者没有诊断入口，只能按顺序走。“专家”和“11 小时”的落差没有在课程里解释，会在阶段 4–5 变成动机断崖（一半内容只能读不能跑，毕业设计则突然要求几十小时的独立工作）。
- 改法：（a）首页加一段“你需要先会什么”：函数、数组方法 map/filter、对象展开、Promise/async，并给一个 8 题的 JS 自测，不及格者先去指定资源；（b）把时长拆成“阅读与练习 11 小时 + 毕业设计 30–60 小时”，把“专家”改写为“具备专家的思维方式，能独立完成三个作品”；（c）为有基础的学习者在首页明确“先做阶段测验，80% 以上可跳过该阶段”，并把阶段测验结果用于推荐起点。

### 中

**M1. 后加的三课信息量过载，与同阶段其他课不成比例。**
- 证据（脚本统计，正文字数不含代码）：第 16 课 DOM 逃生舱 2646 字、7 个小节、5 个目标、6 个 API，标 18 分钟；第 24 课性能测量 3797 字、8 个小节、4 个目标，标 16 分钟；第 26 课无障碍 3456 字、9 个小节、5 个目标，标 18 分钟。同阶段的第 13 课 602 字、第 21 课 859 字。浏览器实测渲染高度：第 16 课 12534px，第 4 课 6729px。
- 为什么影响学习：每课新概念超过 4–5 个会超出工作记忆容量；第 16 课把 forwardRef、useImperativeHandle、useLayoutEffect、createPortal、useId、flushSync 塞进一课，但练习只用到其中两个（createPortal、useId）。第 24 课同时讲 DevTools 面板、`<Profiler>` 参数、Performance 面板、Web Vitals、虚拟列表、React Compiler，练习却是手写虚拟列表（和前五个小节无关）。
- 改法：第 16 课拆成“ref 进阶（forwardRef / useImperativeHandle）”和“Portal、useId、useLayoutEffect”两课，flushSync 降为“深入一点”；第 24 课拆成“测量（Profiler / Performance / Web Vitals）”和“长列表与虚拟化”；第 26 课把“减少动画”“怎样检查”合并为附录。时长估算按 250 字/分钟 + 每个示例 2 分钟 + 练习实测时间重新计算。

**M2. 难度曲线有倒挂；阶段 4 有一半的课没有练习。**
- 证据：第 24 课练习要求从零实现虚拟列表（范围计算、占位高度、绝对定位、scroll 事件），检查 9 条断言；而第 30 课“迷你 React”的练习只要求写 `return { type, props: { ...props, children } }` 一行。第 21 课练习（把 `count + 1` 改成 `c => c + 1`）与第 14 课练习（照抄课内 Clock 示例）几乎零迁移。没有练习的课：23 并发、28 React 19、29 Server Components、31 工程化、37 毕业设计；阶段 4 七课只有四课有练习。预测题分布也不均：阶段 0/1/2/3/4 分别 5、2、8、4、1 个，第 10–13 课（状态提升、reducer、Context、ref）一个预测题都没有。
- 为什么影响学习：练习难度与课程位置脱节，会让学习者对自己的水平判断失准；阶段 4 以阅读为主，正好是最需要“做”来形成判断力的阶段。
- 改法：第 30 课练习改为“实现 render 的更新逻辑：类型相同复用 DOM，只改变化的属性”，或“给迷你 useState 加上函数式更新与批处理”；第 24 课虚拟列表给出 `start/end` 的计算骨架，只让学习者填占位与范围；第 14 课练习改成与课内示例不同的场景（例如订阅 `window.resize` 并在卸载时移除）；第 23 课加“把搜索结果列表放进 startTransition，并用 isPending 显示状态”的练习（环境是 React 18，可运行）；第 10–13 课各加 1 个预测题（例如第 12 课：Provider 的兄弟组件读到什么——现成的 CHECK1 就可以改成预测题）。

**M3. 若干目标没有对应的练习或测验，目标与评估不对齐。**
- 证据：第 18 课目标“用 Context 把 dispatch 交给深层组件”，但练习里 Context 部分已写好、只让写 reducer；第 17 课目标“把逻辑抽成自定义 Hook”，检查程序不验证是否抽成 Hook（只验证界面行为）；第 31 课目标“会为组件写测试”，无练习；第 16 课目标“知道 flushSync 的用途”，无测验题覆盖；第 36 课目标“能独立搭建一个全栈页面”，课内只有一道“解析路由文件夹”的纯函数练习。
- 为什么影响学习：目标是学习者分配注意力的依据；目标说“会做 X”而评估不考 X，学习者会错把“读过”当“会做”。
- 改法：对每课做一张“目标 × 评估”矩阵，没有被任何题或练习覆盖的目标，要么降为“了解”，要么补一题。第 18 课可在检查里加 `t.source` 对 `useContext(DispatchCtx)` 的检查并让学习者自己写 `Card` 的 dispatch 调用。

**M4. 课内测验约四分之一是术语识别题，干扰项显而易见，无法检验理解。**
- 证据：第 7 课 Q1“key 的主要作用是？”（干扰项“给元素加样式”“提高网络请求速度”）；第 25 课 Q1“复合组件通过什么共享状态？”（干扰项 localStorage、URL）、Q3“如今复用有状态逻辑最推荐的方式是？”（干扰项 Mixins）；第 31 课 Q2 干扰项“纯 HTML”“jQuery”；第 37 课 Q2“下面哪个最能证明你真正掌握了 React？”（干扰项“看完了所有教程视频”）；第 33 课 Q2“读取 id 用哪个 Hook？”。通读 102 道课内题，约 25 道属于此类。相比之下 49 道阶段测验专用题几乎全是读代码题。
- 为什么影响学习：这些题进入热身和间隔复习队列后会被反复复习，占用复习配额，却不提供提取练习的价值；排除法就能答对，还会抬高“掌握感”。
- 改法：把这类题从 `quiz` 移到 `checkOnly` 之外的“术语自测”，不进复习队列；或改写成情境题（“同事把 key 写成了 Math.random()，列表会出现什么现象？”）。干扰项应来自真实的常见错误（例如第 7 课的干扰项用 index、用 `item.name`）。

**M5. 阶段测验可当场无限重测，“80% 掌握”不产生任何后果，也没有冷却机制。**
- 证据：`renderCheck` 结束后提供“换一组题再测”立即重新抽题（app.js:825–826）；仅记录 `best` 和 `passed`（app.js:821）；没有任何内容被锁定；提示文字说“过一两天再来测一次”，但不执行。每阶段题库约 30 题，抽 10 题，重测两三次就能覆盖全部题目。
- 为什么影响学习：掌握标准失去约束力，学习者可以通过“多测几次、记住答案”达到 80%。交错测验的诊断价值被稀释。
- 改法：同一阶段 24 小时内最多测一次（本地存时间戳即可）；未达标时下一次测验的题目至少一半来自答错的课；达标后在首页显示“掌握日期”，并在 35 天后把该阶段标记为“待复测”。

**M6. 阶段 4–5 的大部分内容在课程环境里不能运行，“先预测再运行”在这里失效，但页面没有区分“可运行”和“只能读”。**
- 证据：运行环境是 React 18.3.1（build.py:6），第 28 课 React 19 的 Actions / useOptimistic、第 29 课 Server Components、第 33–36 课 Router / Query / 测试 / Next.js 的主要示例都是静态 `code` 块。统计：第 29 课 0 个 play、4 个 code；第 36 课 0 个 play；第 28 课 1 个 play、5 个 code。练习用“迷你版”库代替（迷你路由、迷你 Query、迷你测试库），这是聪明的权宜，但学习者没有被告知“这和真库的差异在哪”（第 33 课检查程序甚至要拦截 `<a href>` 的默认跳转）。
- 为什么影响学习：学习者在前三个阶段建立了“看代码 → 预测 → 运行验证”的习惯，到阶段 4–5 突然只能阅读，而课程没有说明这一变化，也没有提供替代的主动学习方式（例如“在你本地项目里试一下”的任务卡）。
- 改法：（a）在静态代码块上标注“本页不可运行 · 请在本地 Vite 项目中试”，并给出一个最小的本地任务（三行命令 + 要观察什么）；（b）升级运行环境到 React 19，让第 28 课的 Actions / useOptimistic / `use()` 可运行（技术审查也提到这一点）；（c）为每个迷你库加一个“和真库的三点差异”表。

**M7. 毕业设计的课号引用有错，学习路径的回链失效。**
- 证据：lessons-5.js:1298 “受控表单、TypeScript 类型（第 8、29 课）”，第 29 课是 Server Components，TypeScript 是第 32 课；lessons-5.js:1310 “lazy、Suspense、性能优化（第 19、21 课）”，应为第 22、20 课；lessons-5.js:1317 “useOptimistic、reducer（第 25、36 课）”，第 25 课是设计模式，useOptimistic 在第 28 课、reducer 在第 11 课。单课号引用（脚本核对 23 处）都正确，错的是这三处多课号引用，说明重排课序后的更新漏掉了“第 N、M 课”格式。
- 为什么影响学习：毕业设计是学习者最需要回查的地方，回链错误直接浪费时间并损害信任。
- 改法：把课号引用改为按 id 引用（例如 `{ref:'typescript'}`），渲染时再换成当前课号，和 `lessonAfter` 一样动态计算。

### 低

**L1. 复习与热身只用固定的选择题，长期会退化为记住答案位置。** 选项每次打乱（app.js:504）缓解了一部分，但题干和选项文字不变。35 天后第五次见到同一题，学习者记住的是题面而不是概念。改法：为高频概念准备 2–3 个变体题，复习时轮换；或把阶段测验专用题也纳入热身池（现在 `makeWarmup` 只抽 `l.quiz`，app.js:633）。

**L2. 文案与机制不一致。** 第 N 课完成后的提示说“明天会第一次回来找你”（app.js:622），但答错的题 `due = Date.now()`（app.js:543），当天就会出现在“今日复习”；阶段测验结果页说“答错的题会自动加入复习队列”，复习页说“答错了，它明天会再出现”。实测答错后复习页立即出题。改法：统一为“答错的题今天就会再出现一次，答对后进入 1/3/7/16/35 天的间隔”。

**L3. 练习检查里的源码正则会误判合理写法。** 第 4 课要求 `setCount\(` 出现 ≥ 5 次，学习者若写 `const inc = () => setCount(c => c + 1)` 再调用三次 `inc()`，行为正确但被拒；第 12 课要求 `useContext\(\s*UserContext\s*\)`，用 `use(UserContext)` 或先取别名都会失败。这类检查在教学上是在测“写法”而不是“行为”。改法：源码检查只用于禁止反模式（如 `Math.random`、`querySelector`），不用于要求特定调用形式；确有必要时在任务文字里明确写出。

**L4. 第 31 课“工程化、测试与持续成长”与阶段 5 的 TypeScript、测试课重复，且位置尴尬。** 它在阶段 4 末尾讲“你的下一站是第五阶段”，内容是阶段 5 的缩略预告，目标“会为组件写测试”没有练习。改法：改成“项目搭建与交付清单”（Vite 初始化、ESLint、StrictMode、目录结构、CI 三件套），把测试和 TS 的内容删掉，只留指向第 32、35 课的链接。

**L5. 首页的方法说明用“被大量研究验证过”作为论据，但没有任何引用；“简明的写法”声称参考 ASD-STE100。** 对学习者而言这是可信度而不是学习问题；但若课程面向教学同行，建议在术语表页加一节“方法与参考文献”（例如 Roediger & Karpicke 2006 的测试效应、Cepeda 等 2006 的间隔效应、Chi 等 1994 的自我解释、Renkl & Atkinson 的渐隐示例），并说明哪些机制是直接实现、哪些是简化。

**L6. 动机设计单薄。** 完成一课的反馈只有 toast“本课完成！🎉”和进度条；没有“你现在能做什么了”的能力地图，没有里程碑作品（阶段 1–2 的三个项目完成后没有被展示为“作品”）；侧栏数字“已完成 12/37”把 40 分钟的项目和 8 分钟的概念课等权。改法：在阶段卡片上显示“完成本阶段后你能做的事”；把三个实战项目的通过状态单独做成“作品集”区块；进度按时长加权。

## 4. 优先级最高的 5 条改进建议

1. **让预测真正成为预测（H1）。** 为 20 个预测示例准备去剧透版源码（删注释、删 ❌/✅、删结论句），预测后再切回完整版。这是改动最小、对“学习科学设计”这一卖点影响最大的一项：现在约三分之一的预测题答案就在屏幕上。

2. **重做掌握判定（H2 + M5）。** 测验答错后不显示正确字母、重答换变体或延后到热身再验证；阶段测验同一阶段 24 小时一次，未达标时下次半数题来自错题课；把“已掌握”保留给阶段测验，课级只标“已完成”。这样“80% 掌握”才有含义。

3. **把提示阶梯从“计数器”改成“脚手架”（H3）。** 解锁条件加入“代码有实质改动”；为每道练习手写两级渐隐版本（按步骤从后往前挖空，而不是隔行），提示写成“方向 → API → 关键行”三级。先从阶段 1–2 的 18 道练习做起，这里是初学者最需要脚手架的地方。

4. **给自我解释一个可对照的答案（H4）。** 每课写一段 3 句的参考讲法和 3 个必提关键词，学习者写完后并排显示并勾选；同时把 44 条“理解 / 知道 / 了解”型目标改写成可观察的动作。这一项成本是每课 10 分钟的写作，收益是让六个机制中最空的一个开始工作。

5. **交代学习者是谁、路有多长（H5 + M6）。** 首页加先修说明和 8 题 JS 自测；时长改成“课内 11 小时 + 毕业设计 30–60 小时”；为阶段 4–5 的静态代码块加“本页不可运行，去本地试”的任务卡，并考虑把运行环境升到 React 19。配合拆分第 16、24、26 三课（M1），把后半程的认知负荷和动机断崖一起补上。
