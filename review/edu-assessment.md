# 教育测评审查：练习、测验与反馈（2026-10-05）

审查对象：《React 从零到专家》37 课的随堂测验（102 题）、阶段测验专用读代码题（49 题）、预测题（17 题）、动手练习（32 道）以及 app.js 中的测评机制（提示阶梯、自动检查、课前热身、间隔复习、阶段测验、自我解释）。

方法：
- 通读全部 151 道选择题和 32 道练习的任务、starter、参考答案、提示与 `test(t)`。
- 在 Chromium（Playwright）里对 8 道练习（跨 5 个阶段）提交了 16 种“合理但不同的写法 / 常见错误写法 / 投机写法”，记录自动检查的判定和失败信息（脚本与结果在 scratchpad/edu/pc/，未放入共享文件夹）。
- 用二项分布估算阶段测验“10 题 80%”的判定可靠性。
- 与布鲁姆分类、构建式对齐逐课对照目标—活动—测评。

本报告不重复 expert-summary.md 已收紧的约 20 道练习检查；下面提到的检查问题都是本次新发现或本次实测确认的。

## 1. 总评与评分

**总分：6.5 / 10。** 这是一套在“学习活动设计”上明显高于一般教程的课程：先预测再运行、课前热身、Leitner 复习、失败后逐级解锁帮助、自我解释，每个环节都对应一条学习科学原理，而且都真正做进了产品。练习像用户一样操作组件来验收（而不是比对字符串），三个实战项目和测试课的“变异测试”式练习尤其出色。短板集中在**测评的效度与信度**：课内测验以记忆题为主、干扰项偏弱；自动检查里仍有不少“字面检查”，能被投机写法绕过，也会误拒合理写法；掌握标准（测验全对、练习通过、阶段测验 80%）在实现上都可以零成本达到；毕业设计没有任何评估。学生能知道“哪一课没过”，但很难知道“自己真正掌握到什么程度”。

## 2. 主要优点（有证据）

1. **自动检查按“用户行为”验收，而非比对答案文本。** `makeTester`（app.js:397-417）提供 `t.click / t.type / t.byText`，检查像用户一样操作组件。例如 `events` 练习只看点击后 `#status` 的文字变化（lessons-1.js:531-537）；`patterns` 练习用 4 个 Toggle 实例分别覆盖非受控、受控、父组件拒绝更新、`defaultValue+onChange` 四种边界（lessons-4.js:126-135）。实测 `patterns` 的常见错误（用“有没有 onChange”判断受控）在 `#free2` 处被准确拦下。

2. **实战项目是真正的综合评估。** `project-todo` 的检查按需求 1–6 逐条验收，包括空白输入、筛选切换、剩余计数、删除后计数（lessons-1.js 第 9 课 test）；`project-kanban` 既操作 UI，又直接调用导出的 `boardReducer` 验证纯函数性（`JSON.stringify(s0) === snap`、越界不动、id 不重复）；`project-search` 用“李→李四”快速输入检验竞态（需求 7）。这三道题的失败信息都带“（需求 N）”，能直接回到规格。

3. **测试课的练习是“变异测试”。** `lessons-6-ex-testing.js:258-283` 要求学生写测试，然后用正确版本、“一次加两件”和“清空无效”两个 bug 版本分别运行学生的测试，要求前者全过、后两者至少失败一个。这是评估“测试有效性”的正确方式，比检查测试写法本身高明得多。`nextjs` 的 `resolveRoute` 用 CASES 表驱动、逐条报“应是 / 实际是 / 为什么”也属此类。

4. **阶段测验新题（checkOnly）是整套题库里质量最高的部分。** 49 题几乎全是“看代码预测结果”或“找出问题”，干扰项对应真实误解：`state#c0`（队列更新 + 快照）、`custom-hooks#c0`（自定义 Hook 不改变快照规则）、`project-kanban#c0`（StrictMode 下 reducer 的副作用被执行两次）、`router#c1`（`'2' + 1 === '21'`）、`tanstack-query#c1`（前缀失效）。其中 26/49 的解析逐一说明了干扰项为什么错。

5. **预测题设计到位，且以行为验证。** 17 道 PREDICT 题在运行前隐藏说明（app.js:319-321），选项顺序按题目固定打乱（app.js:343-346），选完才能运行并给出“你的预测 / 实际结果 / 解释”。题目都是“点 N 次后显示什么”这类可观察结果，正是生成效应需要的形式。

6. **提示阶梯的第一级确实只“指方向”。** 如 `lists-keys` 的提示“哪个数组方法能留下一部分元素？哪个能把每一项变成 li？key 用哪个字段最稳定？”（lessons-1.js:733）；`escape-hatches` 的提示把学生引回课文的具体示例（lessons-6-escape.js）。失败一次解锁一级（app.js:449-456）在机制上也落实了“先挣扎再求助”。

7. **练习检查先去注释、先重新运行再检查。** `stripComments`（app.js:394-396）和每次检查都 `pg._run()` 重新挂载（app.js:463），避免了“把答案写进注释”和“上一次运行残留状态”两类假通过。

8. **失败信息普遍写成“期望 X，实际 Y，提示方向”。** 例如 `state`：“点 +3 后应从 2 变成 5，实际是 3。连续调用三次时，请用函数式更新”（lessons-1.js:441，实测确认）；`performance`：“点击 2 次 ping 后应为 2，实际是 1。回调是否读到了旧的 pings？”（lessons-3.js:308，实测确认）。

## 3. 问题清单（按严重度排序）

### 高

**H1. “掌握”在实现上可以零成本达成，掌握记录不可信。**
- 证据：
  - 测验答错时直接显示“正确答案是 B”并给出“读懂解析后再答一次”按钮（app.js:521-527）；重答后 `state[qi]` 覆盖为新选择，`quizPassed` 只看最终选择（app.js:581-584）。于是“测验全对”没有任何门槛。
  - 练习失败 3 次后“查看参考答案”把答案直接载入编辑器（app.js:487-489），此时点“检查答案”即通过并写入 `p.ex = true`（app.js:469-471），`maybeComplete` 把课标为完成。界面文字建议“重置后不看答案再写一遍”，但不记录、不强制。
  - 阶段测验 `rec.passed = true` 一旦写入永不撤销（app.js:821），且可无限次“换一组题再测”（app.js:825-826）。
- 影响：首页和侧栏的“已完成 / 已掌握”标记混合了真实掌握和点穿流程，学生自己也无法区分。整个“掌握学习”叙事的可信度建立在这几个标记上。
- 改法：
  1. 测验：首次作答计入“掌握”，重答只用于学习不改变“全对”状态；或者重答时**换同一知识点的变式题**（见 M4）。至少在课内进度显示“首次答对 N/M”。
  2. 练习：载入参考答案后把本次练习标为 `ex: 'viewed'`；要求学生点“重置”后再次通过才记为 `ex: true`；首页统计分开显示“独立通过 / 看过答案”。
  3. 阶段测验：记录每次成绩序列而非只记最好成绩；“再测”至少间隔 1 天（文案已这样建议，机制上不执行）；或者再测时新题池排除已见过的题。

**H2. 字面检查仍能被投机写法绕过，也会误拒合理写法（实测）。**
- 证据（16 种写法实测，脚本见 scratchpad/edu/pc/probe.mjs）：
  - `use-effect`：没有清理函数、只写一句 `const stop = clearInterval;` 即通过（lessons-2.js:155 只检查 `/clearInterval/`）。而“清理函数”正是本课三个目标之一。
  - `closures`：把依赖改成 `[count]`、再加一个空的 `useEffect(() => {}, [])` 即通过（lessons-3.js:417 只检查源码里存在 `}, [])`）。本题的核心约束“依赖保持 []”就失效了。
  - `state`：`setCount(count + 3); setCount(c => c); setCount(c => c);` 通过（lessons-1.js:442 只数 `setCount(` 出现 ≥ 5 次）。
  - `typescript`：`label: any; tone?: 'info' | 'success' | string` 通过（lessons-5.js:153-155 只匹配 `BadgeProps` 和 `'info' | 'success'` 字样）。练习目标“会给 props 写类型”完全没被验证。
  - 误拒：`lists-keys` 把 `<li>` 抽成 `TodoItem` 组件、key 写在 `<TodoItem key={t.id}>` 上被拒（lessons-1.js:738 要求 key 必须写在 `<li` 上）；`context` 写 `const { Provider } = UserContext; <Provider value="小李">` 被拒（lessons-2.js:529）。两者都是课文鼓励的写法。
  - 另外 `lists-keys` 的 `key={i}` 错误和上述合理写法得到**同一条**失败信息，无法区分。
- 影响：被拒的学生会怀疑自己正确的理解；绕过的学生得到假阳性，进度标记失真。
- 改法：
  - `use-effect`：行为验证清理——在检查里卸载组件（`t.root` 重新渲染一个空 App）后 `await t.wait(1200)`，用 `console` 代理或 sandbox 的 `timers` 集合（Runner 已维护 `this.timers`，app.js:110/145）断言没有定时器仍在跑。
  - `closures`：改为检查 effect 的真实依赖——把 `useEffect` 包一层记录依赖数组长度的代理（sandbox 可注入自定义 React 对象），或至少用 AST（Babel 已在页面里，`Babel.transform` 可输出 AST）找出含 `setInterval` 的那个 `useEffect` 调用的第二个参数。
  - `state`：只数 `+3` 按钮处理函数内的 `setCount` 调用（用 AST 定位 `onClick`），或改为行为验证：点 +3 后再点 -1 应为 4，并要求三次调用——这一点用 React 的 `useState` 代理记录 set 调用次数即可。
  - `typescript`：把 TypeScript 编译器（`typescript.js`，~9 MB，可懒加载）引入实验台，对练习做一次 `transpileModule` 之外的 `getPreEmitDiagnostics`；或退一步，用 AST 检查 `label` 的类型注解是 `string`、`tone` 带 `?`、联合只含两个字面量。
  - `lists-keys` / `context`：放宽为“map 直接返回的元素上有 `key={...id}`”和 `/<(UserContext\.)?Provider\s+value=/`；给 `key={i}` 单独的失败信息“你用了下标作 key，列表重排时会错位”。

**H3. 阶段测验 10 题、80% 的判定信度不足，且一半题目是已见过的原题。**
- 证据：`renderCheck` 每次抽 5 道新题 + 5 道课内原题（app.js:805-806）；课内题学生已连同解析看过。二项分布估算（见 scratchpad）：真实掌握率 70% 的学生单次通过概率 38%，3 次重测内 77%；若 5 道旧题按 95% 答对，新题掌握率仅 50% 的学生 3 次内通过概率 81%。每阶段新题池只有 9–10 道（stage 3 为 9），两次测验后新题全部见过。
- 影响：80% 这个数字看起来严谨，实际区分度很低；“✓ 已掌握”对学生和对课程方都不能作为进阶依据。
- 改法：
  1. 题量提到 15–20 题，其中新题 ≥ 10，每阶段新题池扩到 20–30（本次 49 道新题质量高，按同一模板扩写成本可控）。
  2. 旧题改为**变式**而非原题（改数字、改变量名、改为“哪个修法正确”）。
  3. 报告按课分解的得分而不只是一个百分比；把“需要加强”列表和具体错题挂钩（现在只列课名，app.js:824）。
  4. 把练习纳入阶段判定：阶段通过 = 测验 ≥ 80% 且本阶段练习独立通过 ≥ 80%。

### 中

**M1. 课内测验以识记题为主，干扰项偏弱，解析很少解释错误选项。**
- 证据：
  - 约 20 题含“明显荒谬”干扰项：`what-is-react#0`（“React 是一个后端框架”“用 jQuery 操作 DOM 更快”）、`components-props#0`（“大写字母运行更快”）、`state#2`（“let 不能存数字”“React 不支持 let”）、`events#1`（“e.cancel()”）、`lists-keys#0`（“提高网络请求速度”）、`use-ref#0`（“只有在严格模式下会”）、`patterns#2`（“Mixins”）、`engineering#1`（“纯 HTML”“jQuery”）、`portfolio#1`（“背下了所有 Hook 的名字”）、`mini-react#1`（“支持 TypeScript”）。这些题实际是二选一。
  - 术语定义题：`jsx#2`（className）、`components-props#2`（children）、`router#1`（useParams）、`nextjs#0`、`tanstack-query#2`（staleTime 的作用）、`react-19#1`（useOptimistic 的作用）、`server-components#1`（"use server" 标记什么）——布鲁姆“记忆”层。
  - 统计：102 题中 34 题解析不足 30 字（如 `patterns#0`“父组件通过 Context 提供状态……”、`portfolio#0`“先测量，再优化。”）；解析提到任一干扰项的只有 22 题。正确项是最长选项的比例 62%（151 题合计 94 题），这是应试者熟知的线索。
  - 重复题：`performance#2`（“性能优化的第一步”）与 `portfolio#0`（“页面出现卡顿，最先应该做的”）题干、正确项、干扰项几乎相同。
- 影响：课内测验对“看懂了”和“学会了”的区分度低；复习队列里循环的也是这些题，复习效果打折。
- 改法：把弱干扰项替换成真实误解（每个 checkOnly 题都是范例），例如 `use-ref#0` 的干扰项可改为“会，但只在下一次事件后”“会，因为 ref 也是 Hook”；给每题解析加一句“为什么 A/C/D 不对”；把 10 道定义题改为场景题（“下面代码里 staleTime: 0 会导致什么”）；删除 `portfolio#0`；用脚本定期检查“最长选项 = 正确项”的比例并把它压到 ~25%。

**M2. 7 道练习过于轻量，和课程目标的动词不匹配。**
- 证据（参考答案相对 starter 的新行数）：`lifting-state` 2 行（只是解构两个 prop，state 已在父组件，没有“提升”任何东西；目标写的是“会做状态提升”）；`closures` 1 行（提示直接给出修法“把 setCount(count + 1) 改成函数式更新”，lessons-3.js hint）；`mini-react` 1 行（`{ type, props: { ...props, children } }`；目标是“理解 Hooks 为什么依赖调用顺序”“Fiber”，练习与之无关）；`state-architecture` 3 行（`subscribe/get/inc` 各一行，目标“亲手实现迷你 Zustand”）；`use-ref` 3 行；`custom-hooks` 4 行；`performance` 3 行。
- 影响：阶段 2–3 的练习难度反而低于阶段 1 末尾的项目；“专家”阶段的动手量最少（stage 3 共 4 道，新行 7/12/3/1）。
- 改法：
  - `lifting-state`：给两个各自持有 state 的兄弟组件（温度转换器那种），要求学生把 state 提到父组件并保持同步，检查“改一个另一个跟着变”。
  - `closures`：改成“聊天室切换 roomId 后仍收到旧房间消息”的真实过期闭包，要求用依赖或 `useEffectEvent` 式封装修复，检查切换后不再出现旧房间消息。
  - `mini-react`：让学生实现带游标的 `useState`（课文已给 20 行版本可作半成品），检查“两次渲染后状态按顺序对应”“条件调用后错位”。
  - `state-architecture`：加上 `set(partial)` 和 selector + 相等比较，检查“selector 未变的组件不重渲染”（用渲染计数）。

**M3. 半成品示例（渐隐示例）按“隔行遮盖”机械生成，常常遮错行。**
- 证据：`fadedExample`（app.js:420-428）对参考答案中不属于 starter 的行按奇偶交替遮盖。生成结果：`use-effect` 遮住 `useEffect(() => {` 和 `return () => clearInterval(id);`，却完整露出关键行 `const id = setInterval(() => setSeconds(s => s + 1), 1000);`；`closures` 只有 1 行不同，“半成品”等于答案；`state` 在 JSX 子节点位置插入 `/* ✏️ */`，不是合法 JSX，学生照抄会报错。
- 影响：第二级帮助要么泄露答案、要么没有信息量，阶梯的中间一级失去意义。
- 改法：允许练习声明 `fade: [行号或正则]` 指定要遮的关键行，默认才用自动交替；JSX 内用 `{/* ✏️ */}`；当参考答案与 starter 差异 ≤ 2 行时跳过这一级，直接从“提示”到“答案”。

**M4. 间隔复习和课前热身只重放原题原选项，训练的是对题面的再认。**
- 证据：`cardOf`（app.js:546-554）直接取 `l.quiz[n]`，`makeQuestion` 只打乱选项顺序。没有任何变式机制。`makeWarmup` 池子只含 `l.quiz`，不含 checkOnly（app.js:633）。
- 影响：第 2 次之后学生很可能记住“关于 key 的那道题选 id”，而不是概念本身；测验题目本身偏识记（M1）让这个问题更明显。
- 改法：给每道题增加 1–2 个 `variants`（改数字 / 改变量 / 反向问法），复习时轮换；热身题池加入已答过的 checkOnly 题；对预测题也可进入复习（它们天然是应用题，现在 `__pred` 只记一次）。

**M5. 5 课没有动手练习，其中 `concurrent` 完全可以做；`engineering` 既无新题也无练习。**
- 证据：无练习的课：concurrent、react-19、server-components、engineering、portfolio。`concurrent` 目标是“会用 useTransition”“会用 useDeferredValue”（动词“会用”），课内有可运行的标签页演示，但只有 2 道选择题评估。`engineering` 的 `checkOnly` 为 0（stage 3 新题池因此只有 9 道），目标“会为组件写测试”与第 35 课重复。
- 影响：目标—测评不对齐；学生在这些课的“完成”只靠测验（而测验可重答到全对）。
- 改法：`concurrent` 加练习“给一个 5000 项的筛选列表加 useDeferredValue，检查输入框在重渲染期间仍能即时更新”（实验台能跑 React 18，用 `t.type` 后立刻读 `input.value` 即可验证）；`react-19`、`server-components` 虽不能运行，可仿照 nextjs 的做法做纯函数练习（例如实现“哪些 props 可以序列化跨越 server/client 边界”的校验函数，或 `useActionState` 的 reducer 式 action）；`engineering` 并入“项目搭建与交付”并至少补 2 道 checkOnly。

**M6. 部分失败信息只报症状、不指原因。**
- 证据：`use-effect` 过期闭包写法（`setSeconds(seconds + 1)` + `[]`）的反馈是“2.3 秒后应约为 2，实际是 1”（lessons-2.js:158），没有提示“回调读到的是第一次渲染的 seconds”；`lists-keys` 的 `key={i}` 和“key 写在组件上”得到同一句话（见 H2）；`patterns` 的“用 onChange 判断受控”错误被报成“defaultValue={true} 时初始应为开”（lessons-4.js:133），学生要自己反推。
- 改法：在断言里针对可预测的错误值分支输出：`实际是 1` 时追加“每秒都在 setSeconds(0 + 1)？回调记住的是哪一次渲染的 seconds？”；`patterns` 在 `#free2` 失败时追加“free2 传了 onChange 但没传 value，它应该是非受控的。你用什么判断受控？”。

**M7. 没有总结性评估：毕业设计零反馈，自我解释无对照。**
- 证据：`portfolio` 只有 3 道选择题和一份文字清单（“什么时候算做完了”），没有自评量表、没有提交物、没有同伴/自动检查。`makeSelfExplain`（app.js:652-668）把学生的总结和课程目标勾选框并列，但不提供“参考要点”对照，勾选纯自报。
- 影响：课程声称“能讲清楚才算真的懂了”“独立上线项目才算精通”，但两者都不进入任何记录或反馈回路。
- 改法：
  - 毕业设计：把“完成标准”做成可勾选的评分量表（功能 / 状态设计 / 性能 / 无障碍 / 测试 / 部署，各 0–2 分），存入进度；要求填写项目链接和“三个设计取舍”短答，首页展示。
  - 自我解释：每课给 3–4 条“参考要点”（可直接复用 goals + 一个常见坑），点“写好了”后并排显示；记录学生勾选的“能做到”比例并在课程地图显示“自评掌握”和“测验掌握”两条线。

### 低

**L1. 文案与机制不一致。** 答错后 `srsRecord` 设 `due = Date.now()`（app.js:543），题目立刻到期；但课末提示“明天会第一次回来找你”（app.js:622）、复习页说“答错了，它明天会再出现”（app.js:751、761）。建议答错设为 `+1 DAY` 或把文案改成“马上会再出现”。

**L2. 课内题答案位置偏置极端。** 102 题中 85 题 `answer: 1`，49 道新题中 33 题 `answer: 1`。展示时会打乱（app.js:504），学生看不到；但维护者在阅读源码时正确答案总在第二项，暗示出题时可能是“先写正确项再凑干扰项”，这与 M1 的干扰项质量问题一致。

**L3. 提示阶梯的解锁计数从不清零。** `p.fails` 累计（app.js:473），通过后 `p.ex` 永久打开全部帮助。若学生重置后再练（文案鼓励这样做），所有帮助立即可用。建议“重置”时把阶梯恢复为锁定，或显示“本轮失败 n 次”。

**L4. 阶段测验“需要加强”只列课名。** app.js:824 只列出答错题所属的课，不显示错题本身和解析（题目区域还在页面上方，但没有锚点）。建议在结果卡片里直接列出错题 + 一句解析 + “回看第 N 节”。

**L5. `escape-hatches` 练习的导入要求。** 失败信息提示“请保留 `import * as ReactDOM from 'react-dom'`”，但 `prepare()`（app.js:64-83）对 `import * as` 的处理依赖全局 `ReactDOM` 恰好同名；学生若写 `import { createPortal } from 'react-dom'`（课文也教了这种写法）可以通过，但提示文字只提一种。建议提示两种都可。

## 4. 优先级最高的 5 条改进建议

1. **让“掌握”标记只来自独立完成。** 测验以首次作答计分、重答换变式题；练习在载入参考答案后标为“已看答案”，重置并再次通过才算通过；阶段测验记录成绩序列、再测需隔天或换新题。（对应 H1；改动集中在 app.js 的 `makeQuestion/makeQuiz/makeExercise/renderCheck`，一天工作量。）

2. **把剩余的字面检查改为行为或 AST 检查，并放宽合理写法。** 首批：`use-effect`（卸载后定时器必须停止）、`closures`（真实依赖数组）、`state`（+3 处理函数内三次 set）、`typescript`（引入 TS 诊断或 AST 校验）、`lists-keys` 与 `context`（放宽正则、区分 index key 的失败信息）。每改一道都用本报告 probe.mjs 里的投机写法和合理写法回归。（对应 H2、M6。）

3. **扩大并升级阶段测验。** 每阶段新题池扩到 20–30 道（沿用 checkOnly 的“读代码预测/找 bug”模板），每次 15 题、新题 ≥ 10；旧题用变式；结果按课分解并列出错题与解析；把本阶段练习的独立通过率纳入“已掌握”判定。（对应 H3、L4。）

4. **重写约 20 道弱测验题，补齐解析。** 替换荒谬干扰项为真实误解，定义题改场景题，每题解析说明错误选项为什么错，删除重复题 `portfolio#0`，用脚本把“最长选项即正确”的比例压到 25% 左右。顺带给每题加 1 个变式供复习轮换。（对应 M1、M4。）

5. **把轻量练习升级为与目标匹配的任务，并补上 concurrent 练习。** 优先 `lifting-state`（真正提升 state）、`closures`（切换 roomId 的过期闭包）、`mini-react`（实现带游标的 useState）、`state-architecture`（selector + 相等比较）；给 `concurrent` 加 `useDeferredValue` 行为练习；半成品示例改为按练习声明的关键行遮盖。（对应 M2、M3、M5。）
