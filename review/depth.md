# 内容深度评估：这套课能不能把人带到“React 专家”（2026-10-06）

评估对象：`src/lessons-1..5.js`、`lessons-6-*.js`（按 `lessons-6-order.js` 的 37 课顺序）、`lessons-predict.js`、`lessons-6-checks.js`。
评估角度：只看**深度**，即每课讲到了哪一层、学完能达到什么水平、离“专家”差什么。技术正确性见 `expert-*.md`，教学法见 `edu-*-v2.md`，这里不重复。
基本数据：37 课，标注总时长 842 分钟（约 14 小时）；33 道自动检查的练习；4 课没有练习（React 19、Server Components、工程化、毕业设计）；运行环境 React 18.3.1，React 19、Router、Query、Next.js 的真实 API 只能阅读。

## 一、“React 专家”是什么：一个四级能力框架

每级列出可观察的能力。“可观察”指能用一道题、一次代码评审或一个任务验证。

### L1 入门（能照着写）
1. 能用 JSX、props、state、事件、列表、条件渲染和受控表单写出一个单页小应用。
2. 能解释 `UI = f(state)`，知道修改普通变量不会更新界面。
3. 能为列表选对 key，能写不可变更新。
4. 能用 effect 做定时器、请求，并写清理函数。

### L2 能独立工作（能在团队里负责一个功能模块）
1. 能预测一次更新会让哪些组件重新渲染，能解释“state 跟着位置走”。
2. 能发现并修复过期闭包、依赖数组撒谎、竞态、无限循环。
3. 能按“局部 / 服务端 / 全局 / URL / 表单”给 state 分类，并选对工具。
4. 能用 memo/useMemo/useCallback，并说出什么时候不该用。
5. 能用 Router、Query、Testing Library 搭起一个标准的 CRUD 应用，并给核心流程写测试。
6. 能用 TypeScript 给组件和 Hook 写类型。

### L3 高级（能负责一个大型应用的前端架构，能带人）
1. 能用 Profiler、Performance 面板在**陌生代码**里定位瓶颈，并选择结构性优化而不是到处加 memo；懂 INP/LCP 与 React 的关系。
2. 能设计可复用的组件库 API：复合组件、受控/非受控、headless、键盘交互、无障碍、类型安全。
3. 能解释并发渲染：过渡更新的中断与重启、撕裂与 `useSyncExternalStore`、Suspense 与 transition 的配合。
4. 能设计大型应用的状态架构：规范化、派生数据、乐观更新与回滚、跨页面状态、错误与加载状态的统一建模。
5. 懂 SSR / 流式 / 水合 / RSC 的取舍，能判断一个页面该用哪种渲染策略，能修水合不匹配。
6. 能建立错误处理与监控体系：错误边界粒度、全局错误上报、重试策略。

### L4 专家（能对框架级问题做出判断，能影响团队的技术路线）
1. 能从 Fiber、lanes、调度器的角度解释一个奇怪的渲染行为，并预测修改后的结果；读得懂 `react-reconciler` 的主流程。
2. 能设计并实现一个小型框架级抽象：数据获取层（Suspense 资源缓存、预取、去重、瀑布消除）、状态机驱动的复杂交互、虚拟化与大数据渲染。
3. 懂 RSC 的序列化边界、缓存与重新验证模型、流式与选择性水合的实现，能评估一个应用迁移到 RSC 的成本与收益。
4. 能做性能预算与真实案例诊断：包体积、代码分割策略、内存泄漏、长任务拆分，并能量化改进。
5. 能为团队制定测试策略、安全规范（XSS、CSP、Server Function 的鉴权与输入校验）、构建与部署流程（Monorepo、CI、环境变量）。
6. 能评估新特性（Compiler、Activity、ViewTransition、RSC 变化）对自己项目的影响，并领导迁移。

**一个对照指标**：以上 L3 + L4 的 12 项，每项在真实工作中通常需要 10–40 小时有反馈的练习才能掌握。本课程全部内容 14 小时，其中 L3 相关内容约 4 小时，L4 相关内容不到 1 小时。仅从时长看，课程就不可能把人带到 L4。

## 二、逐课深度评估

深度层级定义：
- **用法**：讲 API 怎么用，附带常见坑。
- **原理**：讲清“为什么这样”，能让学习者预测行为。
- **边界取舍**：讲到什么时候不用、替代方案、代价、版本差异。
- **真实迁移**：练习要求在接近真实的复杂度下做决策，或讲到真实项目的架构问题。

## 三、整体判断

### 学完能到哪一级

**L2“能独立工作”扎实，L3“高级”完成约三分之一，L4“专家”基本没有触及。**

理由：
- L1、L2 的每一条能力都有对应的课、可运行演示、预测题和自动检查的练习，而且练习检查到了行为（函数式更新、严格模式下的清理、竞态、selector 跳过渲染）。这部分是课程的强项，深度超过多数同类课程。
- L3 的 6 条中：性能诊断（第 24 课）、组件 API（第 25、26 课）、并发（第 23 课）、状态架构（第 27 课）、SSR/RSC（第 29 课）、错误处理（第 22 课）各有一课，但每课只讲了那条能力的“入口”：有术语、有心智模型、有一个小练习，没有在真实复杂度下的训练。例如第 24 课教了怎样读 Profiler，但练习是写虚拟列表，不是在陌生代码里找瓶颈；第 27 课教了状态分类，但练习是 40 行的 Zustand，不是一个有 10 个页面共享数据的应用。
- L4 的 6 条中，只有“读得懂 reconciler”有一个 20 行 Hooks 实现和 10 行 Fiber 伪代码作为入口；其余 5 条没有内容。

### 与“专家”的差距：缺失或只停在用法层的主题（按重要性排序）

1. **调度与并发内核（完全缺失原理层）**：lanes/优先级、过渡更新的中断与重启、撕裂为什么发生以及 `useSyncExternalStore` 怎样避免它、自动批处理的实现、为什么紧急更新不可中断。现在第 23 课讲“可以被打断”，第 27 课讲“撕裂指不同组件读到不同值”，第 30 课给了伪代码，三处都停在一句话。专家必须能用这套模型解释奇怪的渲染行为。
2. **Suspense 数据获取的真实模式（只有一条 tip）**：抛出 Promise 的机制、资源缓存、`use()` 配合缓存的 Promise、render-as-you-fetch 与瀑布流、预取、Suspense 边界与 transition 的交互、错误边界的重置与重试。这是 React 19 和所有现代框架的数据层基础，课程里没有一个可运行的例子。
3. **流式 SSR、选择性水合与 RSC 的缓存模型（只读且薄）**：第 29 课讲了 RSC 的边界规则，但没讲 `renderToPipeableStream` 的流式输出、Suspense 边界如何决定哪块先可交互、RSC Payload 的缓存与 `revalidatePath` 的作用范围、服务端组合模式（通过 children 把服务端组件塞进客户端组件）、数据瀑布与 `Promise.all`/预加载。专家要能评估迁移成本，现在只能复述概念。
4. **大型应用状态架构（只有分类）**：规范化（存 id 不存副本）、派生选择器的记忆化、乐观更新与并发冲突、跨页面与跨 tab 的状态、持久化与版本迁移、状态机（XState 思想）、服务端状态与客户端状态的同步策略。三个实战项目的 state 都不超过 3 个字段。
5. **真实性能诊断与性能预算（有方法，无案例）**：没有一个“给你一个慢应用，找出 4 个问题并修好”的练习；没有包体积分析、代码分割策略、内存泄漏（订阅未清理、闭包持有大对象）的诊断、长任务拆分、INP 的实测。
6. **组件库 API 设计（只有两个模式）**：headless Hook（返回 prop getters）、polymorphic `as`/asChild、插槽、`useControllableState` 抽象、键盘交互协议（roving tabindex、`aria-activedescendant`）、主题与设计令牌、API 的向后兼容与废弃策略、Storybook 与文档。第 25 课停在 Tabs 和 Toggle。
7. **表单与校验架构（一个片段）**：大表单的受控/非受控取舍、校验的三个时机、schema 校验（zod）客户端与服务端共用、多步表单、异步校验的竞态、React Hook Form 为什么快。
8. **错误处理与监控（只有基础错误边界）**：错误边界的粒度策略、`resetKeys` 与重试、异步错误怎样交给边界、`createRoot` 的 `onUncaughtError`/`onCaughtError`/`onRecoverableError`、全局 `unhandledrejection`、上报与采样、用户可见的降级策略。
9. **事件系统（只有一句“合成事件”）**：React 18 的根容器委托、与原生监听器的顺序、`passive`、与第三方 DOM 库共存、自定义事件。读旧代码和集成图表库时必备。
10. **类型设计的库级能力（有基础，无进阶）**：见第 32 课的说明。
11. **测试策略（有好练习，无体系）**：定时器与 effect 的测试、并发特性的测试、合约测试、端到端示例、测试性能回归。
12. **构建、部署、Monorepo、CI**：第 31 课与第 37 课各一两句，没有可操作内容。
13. **class 组件与旧代码迁移**：第 22 课用 class 写错误边界但从未教 class 语法；专家经常要读和迁移旧代码（类组件、HOC、Redux 老写法）。
14. **动画、国际化、安全进阶（CSP、Trusted Types、CSRF 与 Server Function）**：动画与国际化完全缺失；安全停在 XSS 三条和 Server Function 鉴权。

### 为什么这些缺口难以在当前结构里补上

- **时长**：阶段 4“专家”7 课共 143 分钟，比阶段 1 还短。
- **运行环境**：React 18.3.1 UMD 无打包器、无服务端，意味着 RSC、流式 SSR、Next.js、Router 数据模式、Query 真库都只能阅读。课程已经用“迷你实现”巧妙绕过了一部分（路由、Query、测试、文件路由），但 RSC 和流式没有迷你实现。
- **练习形态**：现有引擎擅长“固定 id + 脚本操作 + 断言 DOM”，这种检查适合封闭题，不适合“设计”“诊断”“权衡”类的开放题。

## 四、练习与项目的深度

### 练习形态统计（33 道）

- **填空/照写型**（给出 faded 骨架，补 1–3 处）：约 20 道。例如第 1–8 课、第 11、12、13、15 课、路由、Query、文件路由、无障碍折叠面板。它们验证“会用”，不要求决策。
- **行为级 bug 修复型**（代码能跑但有错，必须理解原理才能修）：第 4 课（连点两次 +3）、第 14 课（严格模式下的清理）、第 16 课（监听器泄漏）、第 19 课（state 下移）、第 20 课（memo + useCallback + 过期 pings）、第 21 课（聊天室两个叠加 bug）、第 23 课（主线程占用时间 < 60ms）、第 27 课（selector 跳过渲染、不可变）、第 30 课（游标归零、0 与空字符串、if 里的 Hook 错位）、第 24 课（虚拟列表范围与定位）。约 10 道。这些是课程最有价值的练习，检查了行为而不是写法。
- **真正要求判断的**：第 35 课变异测试（必须想清楚“什么断言能抓住 bug”）、第 25 课（必须想清楚“用 value 还是 onChange 判断受控”）、第 10 课（state 放哪里）。约 3 道。
- **开放式/设计型**：0 道。没有一道题让学习者在两种架构之间选择并证明理由、从需求出发设计 state 结构、在 200 行陌生代码里找问题、或重构一个大组件。

结论：练习要求的是“在已知答案形态的前提下把原理用对”，不是“在真实复杂度下做决策”。这对 L2 足够，对 L3 不够，对 L4 完全不适用。

### 三个实战项目

| 项目 | 实际难度 | 决策空间 |
|---|---|---|
| 实战一 待办 | L1 | state 已在起始代码里给出（todos、text、filter），学习者只写事件与派生计算。 |
| 实战二 异步搜索 | L2 | 有真实的竞态；但结构（`useUserSearch`、status 联合）在正文里已经给出，检查又限制了防抖。 |
| 实战三 看板 | L2 | 界面全部写好，只实现三个 reducer 分支；没有要求设计 state、拆组件或处理持久化。 |

三个项目加起来不到 150 行需要学习者自己写的代码，没有一个涉及多页面、多数据源、权限、乐观更新或性能。它们能支持“能独立工作”的结论，不能支持“高级”，更不能支持“专家”。

### 毕业设计

第 37 课的三个项目（记账本 / 电影搜索 / 团队看板）和验收清单，是整套课程里唯一接近 L3 的要求：断网、慢网、空数据、键盘、Profiler、Lighthouse ≥ 90、CI、故意改坏测试。但它：
- 在课程之外完成，没有任何反馈或验证；
- 项目三要求鉴权、数据库、useOptimistic、部署，而这些主题课程里全是只读；
- 没有参考实现、没有阶段里程碑、没有评审标准（例如“设计取舍”写到什么程度算合格）。

它是一份好的路线图，不是能“支撑专家结论”的作品集训练。

## 五、建议

### 定位

**推荐：改名为“React 从零到高级”，第四阶段改名为“原理与架构”，并把“专家”作为第六阶段的目标预留。**

理由：课程对 L2 的覆盖是诚实、扎实且可验证的；对 L3 有入口；对 L4 没有内容。“专家”这个词会让学习者在面试或工作中高估自己，也会让有经验的读者在第四阶段失望（143 分钟、3 道练习、4 课只读）。改名不损失任何内容，反而让第四阶段“原理：亲手实现迷你 React”“状态管理架构”这些标题名副其实。

如果坚持保留“专家”，必须满足两个条件：新增一个阶段（下面 8 项中至少 6 项，约 5–6 小时）；并把毕业设计改为有里程碑和评审标准的作品集训练。否则标题与内容不符。

### 优先补强的 8 项

每项标明：加深哪一课或新增；要讲到什么程度；配什么练习；是否能在 React 18.3.1 单页环境运行与自动检查；预计篇幅。

#### 1. 新增一课：Suspense 数据获取与资源模式（放在第 22 课之后）
- 讲到：抛出 Promise 的机制（可运行：手写 `createResource` 读取时 throw promise）；资源缓存为什么必须在渲染之外创建；render-as-you-fetch 与瀑布流（两个串行请求 vs 并行预取，用请求时间线可视化）；`startTransition` 让已显示内容不被 fallback 替换（可运行演示）；错误边界配合 `key` 重置与重试；与 React 19 `use()` 的对应关系（只读）。
- 练习（可运行、可检查）：给一个页面，用户信息和文章列表串行加载共 1.2 秒。要求改成并行预取并用两个 Suspense 分别显示，总时间 < 0.8 秒；切换用户时用 transition 保留旧界面。检查：模拟接口记录请求发出时间，断言两个请求的发出时间差 < 50ms；断言切换期间旧内容仍在 DOM 中；断言失败后点“重试”能恢复。
- 篇幅：30–35 分钟，正文约 2000 字 + 3 个演示 + 1 道练习。

#### 2. 加深第 23 课（并发）与第 30 课（迷你 React）：调度、优先级与撕裂
- 讲到：lanes 的直觉模型（紧急 / 过渡 / 空闲三档即可）；过渡渲染被打断后从头重启的成本；为什么提交必须同步；撕裂的可运行复现（在 18.3.1 中：一个模块级可变 store，组件用 `useState + subscribe` 读取，在 `startTransition` 渲染慢列表期间修改 store，列表前后两半显示不同的值），再换成 `useSyncExternalStore` 消除撕裂；`useSyncExternalStore` 为什么会让过渡退化为同步。
- 练习（可运行、可检查）：补全一个 60 行的迷你调度器：用 `MessageChannel` 做时间片，工作单元可中断，有两档优先级，高优先级到来时丢弃低优先级的未完成结果。检查：注入一个慢任务和一个紧急任务，断言紧急任务的完成时间 < 20ms、慢任务被重新开始（计数器 ≥ 2）、最终输出一致。另一道小练习：用 `useSyncExternalStore` 修复撕裂演示，检查渲染结果中所有行的值相同。
- 篇幅：在两课各加约 1200 字和 1 道练习，共约 35 分钟。

#### 3. 新增一课：大型应用状态架构实战（放在第 27 课之后）
- 讲到：规范化（`byId` + `ids`）与为什么存 id 不存副本；派生选择器的记忆化（手写一个 `createSelector`）；乐观更新遇到并发编辑时的冲突与回滚顺序；撤销/重做用 reducer 历史实现；用状态机描述多步流程（结账：idle → validating → paying → done/failed），非法转移写不出来；持久化与版本迁移（`version` 字段 + migrate 函数）。
- 练习（可运行、可检查）：给一个已规范化的 store 和 UI，实现：① `selectVisibleTodos` 在无关 state 变化时不重新计算（检查：计算次数计数器）；② 乐观删除后服务器失败要回滚且保持顺序；③ 撤销/重做。检查用 `store.getState()` 和 DOM 共同断言。
- 篇幅：40–45 分钟。

#### 4. 新增一课：性能诊断实战（放在第 24 课之后）
- 讲到：把前几课的工具用在**陌生代码**上的流程；四类典型问题的 Profiler 特征（Context value 新对象 → 所有消费者一起黄；组件内定义组件 → 每次 mount；大列表 → 布局时间长；effect 链 → 一次操作多次提交）；内存泄漏的诊断（未清理订阅、闭包持有大数组）；包体积与代码分割（只读）。
- 练习（可运行、可检查）：一个 200 行的“仪表盘”应用，埋 4 个问题（Context value 内联对象、组件内定义组件、500 行列表未虚拟化、订阅未清理）。要求修好，且**不改变功能**。检查：用 `<Profiler>` 包住根，断言打字时某次提交的 `actualDuration` < 阈值；断言 `.row` 数量 ≤ 60；断言卸载后 `listeners.size === 0`；断言输入框在重新渲染后仍保持焦点（组件内定义组件已修）；再跑一遍功能断言确认行为没变。
- 篇幅：40–45 分钟。

#### 5. 加深第 25 课（设计模式）：组件库 API 设计
- 讲到：headless Hook 返回 prop getters（`getButtonProps()`）；`useControllableState` 作为受控/非受控的通用抽象；polymorphic `as` 与插槽/`asChild`（含 TypeScript 写法，只读）；键盘交互协议（WAI-ARIA 的 Listbox/Combobox 模式、roving tabindex、`aria-activedescendant`）；API 的兼容演进（新增 prop 不破坏旧用法、废弃策略）；Storybook 一段（只读）。
- 练习（可运行、可检查）：实现 `useListbox` Hook 并用它做一个可访问的下拉选择：ArrowUp/Down 移动高亮、Enter 选中、Escape 关闭、Home/End、输入首字母跳转；同时支持受控 `value` 和非受控 `defaultValue`。检查：派发 `keydown` 事件后断言 `aria-activedescendant`、`aria-selected`、`aria-expanded`，以及受控模式下父组件拒绝更新时值不变。
- 篇幅：加约 1500 字，练习 1 道，共约 40 分钟。

#### 6. 新增一课：错误处理与监控（放在第 22 课之后，或与第 1 项合并）
- 讲到：错误边界的粒度策略（页面 / 路由 / 小部件）；`resetKeys` 与“重试”的实现；异步错误怎样交给边界（在 catch 里 setState 后在渲染中 throw）；`createRoot` 的 `onRecoverableError`（18.3.1 可运行）以及 19 的 `onUncaughtError`/`onCaughtError`（只读）；`window.onerror` 与 `unhandledrejection` 的上报队列与采样；用户可见的降级：保留已加载内容、提供重试、不丢输入。
- 练习（可运行、可检查）：实现 `ErrorBoundary`，支持 `fallback` 渲染函数（拿到 error 与 `reset`）、`resetKeys`、`onError` 上报；再实现 `useAsyncError` 把事件处理函数里的异步错误抛给边界。检查：触发渲染错误与异步错误各一次，断言 fallback 出现、`onError` 被调用且带 componentStack、点重试后恢复、`resetKeys` 变化时自动恢复。
- 篇幅：30 分钟。

#### 7. 加深第 29 课（Server Components）：流式 SSR、选择性水合与 RSC 缓存
- 讲到（只读为主）：`renderToPipeableStream` 的输出顺序与 Suspense 边界的关系；选择性水合：哪块先可交互由用户点击决定；RSC Payload 的缓存与 `revalidatePath`/`revalidateTag` 的作用范围；服务端组合模式（客户端组件通过 children 接收服务端组件）；数据瀑布与 `Promise.all`/预加载；“什么时候不该用 RSC”（纯客户端工具、强交互编辑器、团队没有 Node 服务）。
- 练习（可运行、可检查）：18.3.1 UMD 里有 `ReactDOM.hydrateRoot`。给容器预填一段“服务端 HTML”，学习者的组件要在首次渲染时输出与之完全一致的内容（时间、`window.innerWidth`、随机 id 三处会不匹配），再在 effect 中更新为客户端的值。检查：拦截 `console.error`，断言没有水合警告；断言 effect 后 DOM 显示了客户端的值；断言用了 `useId` 而不是随机数。
- 篇幅：加约 1800 字和 1 道练习，共约 35 分钟。

#### 8. 新增一课：表单与校验架构（放在第 28 课之后）
- 讲到：大表单的受控/非受控取舍与性能原因；校验的三个时机与浏览器原生校验；schema 校验（手写一个 30 行的迷你 zod：`string().min()`、`object()`、`parse` 返回字段级错误）同一份规则在客户端和服务端共用；多步表单用 reducer 保存各步数据与当前步；异步校验（用户名是否可用）的竞态；可访问的错误提示；React Hook Form 的原理一段（只读）。
- 练习（可运行、可检查）：三步注册表单：每步 `FormData` 读取、schema 校验、错误显示在字段旁且 `aria-describedby` 关联；上一步数据保留；异步校验用户名时快速改输入只采用最后一次结果。检查：填错后断言错误文字与 aria 关联；返回上一步断言值仍在；模拟慢的用户名校验断言最终结果正确。
- 篇幅：35 分钟。

以上 8 项共约 5 小时。做完后，L3 的 6 条能力各有一课且各有一道行为级练习，课程可以诚实地叫“从零到高级”，并写明“专家需要在此基础上完成第 37 课的三个项目并通过评审”。L4 的调度器内核、RSC 实现、性能预算等仍需真实项目和源码阅读，课程可以作为“专家路线图”指向它们，但不宜宣称能教到。

### 两条配套建议（非内容深度，但影响“专家”结论能否成立）

1. 把毕业设计改成有里程碑的作品集训练：每个项目拆成 4–5 个里程碑，每个里程碑给验收清单和一份“评审问题”（例如“为什么收藏列表放 Zustand 而不是 Query 缓存？”），并提供参考实现的仓库链接。
2. 在阶段 3、4 的阶段测验里加入“读 150 行代码找 3 个问题”的开放题（可以用多选实现：列出 8 个候选问题，选出真正存在的 3 个），让测验也能检验诊断能力，而不只是单点知识。
