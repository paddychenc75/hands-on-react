# 渲染机制：React 到底做了什么

很多性能问题和奇怪的 bug 都有同一个根源。那就是没搞清楚 React 的渲染过程。这一课我们打开引擎盖看一看。

本课的示例运行在没有 React Compiler 的实验台上，所以你看到的是 React 的默认行为。如果你的项目启用了 React Compiler，部分“子组件跟着重新渲染”的现象会被它消除。第 20 课会讲。

## 什么会触发重新渲染？

- 组件自己的 **state 变化**
- **父组件重新渲染**（默认情况下，所有子组件也会跟着重新渲染，不管 props 有没有变！）
- 它读取的 **Context 值变化**

还有两个细节：

1. **自动批处理**：同一个事件中多次调用 set 函数，只触发一次渲染。React 18 起，setTimeout 和 Promise 回调中也是这样。
2. **同值跳过**：新值与旧值用 `Object.is` 比较相等时，React 跳过这次更新。个别情况下，React 会先调用一次你的组件函数再放弃这次更新。这时它不会渲染子组件，也不会运行 effect。

<CallBox kind="warn" label="常见坑">

一个常见误解是“props 变了组件才会重新渲染”。实际上，**父组件渲染时，子组件默认一律重新渲染**。React 在渲染阶段算出差异，提交阶段只修改变化的 DOM。所以多数时候这并不会造成问题。只有当子组件非常“重”，而且改结构解决不了时，才需要用[性能优化](/lessons/performance)一课的 memo 来优化。

</CallBox>

下面的演示会让每次渲染的组件**闪烁**一下。点击不同的按钮，观察哪些组件被重新渲染：

```jsx play title="谁被重新渲染了？"
import { useState, useRef, useEffect } from 'react';

// 一个会在每次渲染后闪烁的小盒子
function Box({ name, children }) {
  const ref = useRef(null);
  const count = useRef(0);
  count.current++; // 仅用于演示计数：正式代码不要在渲染时读写 ref
  useEffect(() => {
    const el = ref.current;
    el.animate([{ background: '#ffd36b' }, { background: 'transparent' }], { duration: 600 });
  });
  return (
    <div ref={ref} style={{ border: '1px solid #8aa', borderRadius: 8, padding: 8, margin: 6 }}>
      <b>{name}</b> <small>渲染 {count.current} 次</small>
      {children}
    </div>
  );
}

function Child({ label }) {
  return <Box name={'Child ' + label} />;
}

function Counter() {
  const [n, setN] = useState(0);
  return (
    <Box name="Counter（自带 state）">
      <button onClick={() => setN(n + 1)}>Counter 内部 +1：{n}</button>
    </Box>
  );
}

function App() {
  const [count, setCount] = useState(0);
  return (
    <Box name="App">
      <button onClick={() => setCount(count + 1)}>App 的 state +1：{count}</button>
      <Child label="A" />
      <Child label={'B ' + count} />
      <Counter />
    </Box>
  );
}
```

## 先改结构，再考虑 memo

从刚才的演示出发：点 Counter 的按钮，只有 Counter 闪烁。因为 state 在 Counter 里，App 没有重新渲染。

所以，想让一次更新少带动几个组件，就把 state 放进真正用它的最小组件。这叫**把 state 下移**。

```jsx title="只读：把 state 下移"
// 之前：text 在 App 里，每次打字，App 和 Slow 都重新渲染
function App() {
  const [text, setText] = useState('');
  return (
    <>
      <input value={text} onChange={e => setText(e.target.value)} />
      <Slow />
    </>
  );
}

// 之后：text 只在 TextInput 里，打字时 App 不渲染，Slow 也不渲染
function TextInput() {
  const [text, setText] = useState('');
  return <input value={text} onChange={e => setText(e.target.value)} />;
}
function App() {
  return (
    <>
      <TextInput />
      <Slow />
    </>
  );
}
```

另一种结构：把不变的内容作为 children 传进有 state 的组件。children 是外层创建的元素，外层没有重新渲染，它就是同一个对象，React 会跳过它。

```jsx title="只读：用 children 跳过渲染"
function Tabs({ children }) {
  const [tab, setTab] = useState(0); // Tabs 自己的 state 变化时
  return <div><button onClick={() => setTab(tab + 1)}>{tab}</button>{children}</div>;
}
function App() {
  return <Tabs><Slow /></Tabs>; // <Slow /> 由 App 创建；App 没渲染，Slow 就被跳过
}
```

注意边界：只有 Tabs 自己的 state 变化时，children 才会被跳过。创建它的 App 重新渲染时，会创建新的元素，Slow 照样渲染。

## 虚拟 DOM 与协调（Reconciliation）

组件返回的 React 元素树常被称为**虚拟 DOM**：它是用普通 JS 对象描述的界面结构。每次渲染后，React 对比新树和旧树，找出需要的改动，再修改真实 DOM。这个过程叫**协调**。

完美地比较两棵树，复杂度是 O(n³)。n 是元素数量，n³ 意味着 1000 个元素要比较 10 亿次，太慢了。React 基于两个假设，把它降到了 O(n)，也就是 1000 个元素大约比较 1000 次：

- **类型不同的元素会产生完全不同的树**。如果 `<div>` 变成了 `<section>`，或 `<Counter>` 变成了 `<Timer>`，React 会卸载整棵旧子树，丢弃其中所有 state。然后它挂载新的子树。
- **通过 key 识别列表中的元素**。同一层级中，key 相同就认为是同一个元素。

## 状态与位置绑定

这两个假设决定了一件事：组件切换时，它的 state 是保留还是丢弃？先看演示，预测三种情况的结果。

```jsx play title="状态跟着位置走"
import { useState } from 'react';

function Counter({ color }) {
  const [n, setN] = useState(0);
  return <button style={{ color }} onClick={() => setN(n + 1)}>{color} 计数：{n}</button>;
}

function App() {
  const [red, setRed] = useState(false);
  return (
    <div>
      <label><input type="checkbox" checked={red} onChange={e => setRed(e.target.checked)} /> 红色</label>
      <h4>情况 1</h4>
      {red ? <Counter color="red" /> : <Counter color="blue" />}
      <h4>情况 2</h4>
      {red ? <div><Counter color="red" /></div> : <section><Counter color="blue" /></section>}
      <h4>情况 3</h4>
      {red ? <Counter key="r" color="red" /> : <Counter key="b" color="blue" />}
    </div>
  );
}
```

结论：**React 根据组件在树中的“位置”来保存它的 state**。同一位置渲染同一类型的组件，state 会被保留。位置、类型或 key 变了，state 就会丢失。

<CallBox kind="warn" label="常见坑">

**永远不要在组件内部定义组件**。例如在 App 函数体里写 `function Input() {...}`。每次 App 渲染，都会创建一个“新类型”的 Input。结果是每次输入后，Input 的 state 和焦点都会丢失。

</CallBox>

## 隐藏界面，但保留 state：`<Activity>`

上一节说，位置、类型或 key 一变，state 就丢了。可有时你想“隐藏”一块界面，例如切换标签页或收起侧边栏，又不想丢掉用户已经输入的内容。

条件渲染做不到，因为它把组件卸载了。React 19.2 起稳定的 `<Activity>` 能做到。它的 `mode` 属性只有两个值：`"visible"` 和 `"hidden"`。

```jsx play title="三种隐藏方式"
import { Activity, useState, useEffect } from 'react';

function Draft({ name }) {
  const [text, setText] = useState('');
  useEffect(() => {
    console.log(name + '：effect 开始');
    return () => console.log(name + '：effect 清理');
  }, [name]);
  return <input value={text} onChange={e => setText(e.target.value)} placeholder={name} />;
}

function App() {
  const [show, setShow] = useState(true);
  return (
    <div>
      <button onClick={() => setShow(!show)}>{show ? '隐藏' : '显示'}</button>
      <div>{show && <Draft name="条件渲染" />}</div>
      <div style={{ display: show ? 'block' : 'none' }}>
        <Draft name="CSS 隐藏" />
      </div>
      <Activity mode={show ? 'visible' : 'hidden'}>
        <Draft name="Activity" />
      </Activity>
    </div>
  );
}
```

`mode="hidden"` 时，React 做三件事：

1. 用 `display: none` 隐藏子树的 DOM。DOM 和 state 都留着。
2. 清理子树里的 effect，就像卸载一样。
3. 子树仍会随新的 props 重新渲染，但优先级比可见的内容低。

切回 `"visible"` 时，state 原样恢复，effect 重新运行。三种隐藏方式的对比：

| 做法 | state | effect | 隐藏时的渲染 |
|---|---|---|---|
| 条件渲染 `{show && <Page />}` | 丢失 | 卸载时清理 | 不渲染 |
| CSS `display: none` | 保留 | 一直在运行 | 照常重新渲染 |
| `<Activity mode="hidden">` | 保留 | 被清理，显示时重新运行 | 低优先级重新渲染 |

<CallBox kind="warn" label="常见坑">

Activity 隐藏的是 DOM，不会替你停掉有副作用的 DOM。隐藏的 `<video>` 会继续播放。要在 effect 的清理函数里暂停它。

另外，只渲染文字的组件没有 DOM 元素可以隐藏，所以 `hidden` 时什么也不渲染。保留 state 也有代价：隐藏的子树仍占着内存，还会重新渲染。只对来回切换的界面使用它。

</CallBox>

## 严格模式做了什么

**严格模式**（`StrictMode`）是只在开发环境生效的检查工具。它在组件外面包一层 `<StrictMode>` 就能打开。它做两件事：

- 把组件函数、`useState` 的初始化函数和更新函数各多调用一次，用来暴露渲染里的副作用。
- 让每个 effect 多做一轮“开始同步 → 停止同步 → 再开始同步”（第 14 课讲过）。

生产环境没有这些额外调用。

为什么要多调用一次？因为渲染必须是纯的：同样的 props 和 state，一定返回同样的 JSX，渲染时不修改外部的东西。React 可以随时丢弃一次渲染再重来（并发渲染就是这样）。如果组件在渲染时改了外部变量，多调用一次就会让结果出错。严格模式让这类问题在开发时马上出现。

```jsx play title="严格模式下的组件函数"
import { StrictMode, useState } from 'react';

function Demo() {
  const [n, setN] = useState(0);
  console.log('Demo 函数被调用');
  return <button onClick={() => setN(n + 1)}>点击次数：{n}</button>;
}

function App() {
  return (
    <StrictMode>
      <Demo />
    </StrictMode>
  );
}
```

</CallBox>
