第 8 课写了受控表单，第 27 课给字段加了 label 和错误提示，第 29 课看了表单 Actions。这些都是单个技巧。真实的注册、下单、设置页面要把它们组合起来，还会遇到新的问题：字段多了会卡；规则在客户端和服务器各写一遍，慢慢就不一致；用户名检查的结果乱序返回；用户连点两次，订单提交了两次。

本课把一个表单拆成五个决策，最后看 React 19 的 Actions 怎样接管其中几个。每个决策都有默认答案，也有不适用的情况。

## 一、数据放在哪里：受控、非受控与 FormData

**受控**：每个字段的值在 state 里，输入框只显示它。**非受控**：值留在 DOM 里，需要时再读。**FormData** 是浏览器提供的对象：`new FormData(form)` 一次读出表单里所有带 `name` 的字段。

受控写法简单直观，但有一个代价：每输入一个字，保存 state 的组件就重新渲染一次，它下面的所有字段也跟着重新渲染。先预测，再运行。

```jsx play title="每输入一个字，谁在重新渲染？"
import { useState, useRef } from 'react';

const NAMES = ['姓名', '电话', '城市', '街道', '邮编', '备注'];

function Field({ name, value, onChange }) {
  const renders = useRef(0);
  renders.current++;
  const valueProps = onChange ? { value, onChange } : { defaultValue: '' };
  return (
    <label style={{ display: 'block', fontSize: 13, margin: '2px 0' }}>
      {name} <input name={name} {...valueProps} style={{ width: 90 }} />{' '}
      <small style={{ color: '#888' }}>渲染 {renders.current} 次</small>
    </label>
  );
}

function ControlledForm() {
  const [values, setValues] = useState({});
  return (
    <form>
      <b>受控</b>
      {NAMES.map(n => (
        <Field key={n} name={n} value={values[n] ?? ''}
          onChange={e => setValues(v => ({ ...v, [n]: e.target.value }))} />
      ))}
    </form>
  );
}

function UncontrolledForm() {
  function handleSubmit(e) {
    e.preventDefault();
    console.log(Object.fromEntries(new FormData(e.currentTarget)));
  }
  return (
    <form onSubmit={handleSubmit}>
      <b>非受控 + FormData</b>
      {NAMES.map(n => <Field key={n} name={n} />)}
      <button>提交（看控制台）</button>
    </form>
  );
}

function App() {
  return (
    <div style={{ display: 'flex', gap: 24, flexWrap: 'wrap' }}>
      <ControlledForm />
      <UncontrolledForm />
    </div>
  );
}
```

|  | 受控 | 非受控 + FormData |
|---|---|---|
| 值在哪里 | state | DOM |
| 输入时重新渲染 | 保存 state 的组件及其子树 | 没有 |
| 适合 | 输入时就要格式化、字段之间联动、实时预览 | 字段多、只在提交时用值 |
| 难点 | 大表单的性能 | 联动和“边输入边校验”要另外处理 |

React 19 的 `<form action={fn}>` 就建立在这个思路上：提交时 React 把 FormData 直接交给 `fn`（第七节）。

两者可以混用：大部分字段非受控，少数需要联动的字段受控。React Hook Form 的思路更进一步：字段默认非受控，用 ref 注册；打字不触发 React 渲染；错误、是否提交中这类表单状态要读取了才订阅，没读的状态变化不会引起渲染（见本课最后的选读）。

## 二、一份规则，两端共用：schema

校验规则如果散落在各个 onChange 里，很快就会出现“前端说合法、后端说不合法”。**schema** 是一份用数据描述的规则：每个字段是什么类型、要满足哪些条件、失败时显示什么。客户端和服务器导入同一份 schema。

Zod 是最常用的 schema 库。它的核心思想不复杂，下面用 25 行写一个迷你版：`s.string().min(3, 信息)` 描述一个字段，`s.object({...}).safeParse(数据)` 返回每个字段的第一条错误。

```jsx play title="迷你 schema"
function stringSchema(checks = []) {
  // 每个方法都返回一个新的 schema，不修改原来的
  const add = (fn) => stringSchema([...checks, fn]);
  return {
    min: (n, msg) => add(v => v.length >= n || msg),
    email: (msg) => add(v => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v) || msg),
    check(value) {
      const v = typeof value === 'string' ? value : '';
      for (const fn of checks) {
        const r = fn(v);
        if (r !== true) return r; // 返回第一条错误信息
      }
      return null;
    },
  };
}

const s = {
  string: () => stringSchema(),
  object: (shape) => ({
    safeParse(data) {
      const errors = {};
      for (const key of Object.keys(shape)) {
        const msg = shape[key].check(data[key]);
        if (msg) errors[key] = msg;
      }
      return Object.keys(errors).length ? { success: false, errors } : { success: true, data };
    },
  }),
};

const signupSchema = s.object({
  username: s.string().min(3, '用户名至少 3 个字符'),
  email: s.string().email('邮箱格式不正确'),
});

// 链式调用不会修改原来的 schema
const base = s.string();
const short = base.min(2, '至少 2 个字');
const long = base.min(6, '至少 6 个字');

function App() {
  const cases = [
    { username: 'ab', email: 'x' },
    { username: 'alice', email: 'alice@example.com' },
  ];
  return (
    <div>
      {cases.map((c, i) => (
        <pre key={i} style={{ fontSize: 12, whiteSpace: 'pre-wrap', wordBreak: 'break-all' }}>
          {JSON.stringify(c)} → {JSON.stringify(signupSchema.safeParse(c))}
        </pre>
      ))}
      <p>short.check('abc')：{String(short.check('abc'))}</p>
      <p>long.check('abc')：{String(long.check('abc'))}</p>
    </div>
  );
}
```

真实的 Zod 4 里，邮箱这类格式写成顶层函数 `z.email()`。它还会做两件迷你版没做的事：把数据转换成目标类型（例如把字符串 "18" 变成数字 18），以及从 schema 推导 TypeScript 类型（`z.infer<typeof schema>`），表单的类型就不用再写一遍。

<CallBox kind="tip" label="TS 写法">

用 TypeScript 时，表单值的类型从 schema 推导，不手写第二遍：`type SignupValues = z.infer<typeof signupSchema>`。改了 schema，类型自动跟着变，表单代码里用错字段名会在编辑器里报错。

</CallBox>

<CallBox kind="warn" label="常见坑">

<strong>客户端校验只是体验。</strong>任何人都能绕过页面直接发请求。服务器必须用同一份 schema 再校验一次，并把字段错误返回给页面。有些规则只有服务器能检查，例如“用户名唯一”，最终要靠数据库的唯一约束。

</CallBox>

## 三、什么时候显示错误

错误什么时候**算**和什么时候**显示**是两件事。错误可以每次渲染都从当前值算出来，它是派生数据，不需要存进 state。需要存的只是显示条件：

- **touched**（已触碰）：用户进入过这个字段，又离开了（发生过 blur）。
- **dirty**（已修改）：当前值和初始值不同。
- **submitted**（已提交过）：用户点过一次提交。

| 显示时机 | 效果 | 评价 |
|---|---|---|
| 输入时（onChange） | 反馈最快 | 用户刚打第一个字就看到“邮箱格式不正确”，像在被批评 |
| 离开时（touched） | 用户写完再提醒 | 最常用的默认值 |
| 只在提交时 | 最安静 | 20 个字段填完才发现第 2 个就错了 |
| 离开时显示，显示后输入时更新 | 晚提醒，早消除 | 推荐：一改对，错误马上消失 |

推荐的规则写成一行就是：`显示 = (touched[字段] || submitted) && errors[字段]`。因为 errors 每次渲染都重新算，错误一旦显示，用户每输入一个字它都会更新，改对后立刻消失。

为什么用 touched 而不是 dirty？用户 Tab 经过一个必填字段、什么都没填就离开，dirty 是 false，错误不会出现。可这正是该提醒的时候。

错误要能被读屏软件读到。第 27 课讲过三件套：`aria-invalid`、`aria-describedby` 指向错误文字、错误文字说明怎样改。表单级还要再做两件事：

- 提交失败时，把焦点移到第一个出错的字段。否则键盘用户不知道问题在哪里。
- 不要给每个字段的错误都加 `role="alert"`。用户离开一个字段就被打断一次。字段错误靠 aria-describedby，在聚焦时读出就够了。

## 四、异步校验与竞态

“用户名是否已被占用”只有服务器知道。用户每输入一个字就可能发一次请求，而请求的返回顺序和发出顺序不一定相同。结果取决于谁先返回，这就是**竞态**。下面的服务器故意让短名字返回得更慢。先预测，再运行。

```jsx play title="用户名检查的竞态"
import { useState, useEffect } from 'react';

const TAKEN = ['ann', 'admin'];
// 名字越短，服务器越慢：ann 要 600ms，anna 只要 300ms
function checkName(name) {
  const ms = 1500 - name.length * 300;
  return new Promise(resolve => setTimeout(() => resolve(!TAKEN.includes(name)), ms));
}

function NaiveCheck({ name }) {
  const [msg, setMsg] = useState('');
  useEffect(() => {
    if (!name) return;
    setMsg('检查中…');
    checkName(name).then(ok => setMsg(ok ? '可用' : '已被占用'));
  }, [name]);
  return <p>无保护：<b>{msg}</b></p>;
}

function GuardedCheck({ name }) {
  const [msg, setMsg] = useState('');
  useEffect(() => {
    if (!name) return;
    let ignore = false;
    setMsg('检查中…');
    checkName(name).then(ok => { if (!ignore) setMsg(ok ? '可用' : '已被占用'); });
    return () => { ignore = true; };
  }, [name]);
  return <p>有保护：<b>{msg}</b></p>;
}

function App() {
  const [name, setName] = useState('');
  function typeFast() {
    setName('ann');
    setTimeout(() => setName('anna'), 100);
  }
  return (
    <div>
      <input value={name} onChange={e => setName(e.target.value)} placeholder="用户名" />{' '}
      <button onClick={typeFast}>模拟快速输入 ann → anna</button>
      <NaiveCheck name={name} />
      <GuardedCheck name={name} />
    </div>
  );
}
```

修法有三种，原理相同：每个结果都要能回答“我还是最新的吗”。

- **effect 的 ignore 标记**（上面的写法）：值变化时清理函数让旧请求失效。
- **请求序号**：在事件处理函数里发请求时，用 ref 保存一个递增的序号。结果回来时，序号不是最新的就丢弃。
- **AbortController**：直接取消旧请求，还能省下网络流量。被取消的 fetch 会抛出 AbortError，要在 catch 里忽略它。

再加上 200–300ms 的**防抖**，用户连续打字时只发最后一次请求。但防抖不能代替上面三种修法：用户停顿超过防抖时间后又继续输入，两个请求照样会同时在路上。

<CallBox kind="warn" label="常见坑">

检查结果要和**值**一起保存，例如 `{ name: "anna", status: "available" }`。提交时比较 name 是不是当前的用户名，状态还是“检查中”就不能提交。只存一个 `available: true`，就不知道它是哪个名字的结果。

</CallBox>

## 五、多步表单：用 reducer 保存每一步

注册分三步：账号、资料、确认。常见的错误是每一步的组件用自己的 useState 保存字段。切到下一步时，上一步的组件被卸载，state 随之丢失，点“上一步”看到的是空表单。

解决办法是把所有步骤的数据和当前步数提升到父组件，用一个 reducer 管理（第 12 课）。每一步只负责收集和校验自己的字段。

```jsx title="多步表单：数据在 reducer 里，步骤组件可以随意卸载"
const initial = { step: 0, data: { account: {}, profile: {} } };

function reducer(state, action) {
  switch (action.type) {
    case 'saveStep':   // 保存当前步，再前进
      return { step: state.step + 1, data: { ...state.data, [action.key]: action.values } };
    case 'back':       // 返回时也保存当前的输入，否则来回切换会丢掉这一步
      return { step: state.step - 1, data: { ...state.data, [action.key]: action.values } };
    default:
      throw new Error('未知的 action：' + action.type);
  }
}

function AccountStep({ saved, dispatch }) {
  const [errors, setErrors] = useState({});
  function handleSubmit(e) {
    e.preventDefault();
    const values = Object.fromEntries(new FormData(e.currentTarget));
    const result = accountSchema.safeParse(values);   // 每一步一份 schema
    if (!result.success) return setErrors(result.errors);
    dispatch({ type: 'saveStep', key: 'account', values });
  }
  // 非受控字段：用 defaultValue 填回 reducer 里保存的值
  return <form onSubmit={handleSubmit}><input name="email" defaultValue={saved.email} />…</form>;
}
```

这种结构还带来两个好处。最后一步可以用三份子 schema 合起来再校验一次，防止用户改了前面的数据却跳过校验；“确认”页直接读 reducer 的 data，不需要再从各步收集。

## 六、提交：pending 与防重复

提交期间要做三件事：按钮禁用并显示“提交中…”；防止重复提交；结束后无论成功失败都恢复。前两件看起来是一件事，其实不是。

按钮的 `disabled` 来自 state，它要等重新渲染后才生效。在 React 重新渲染之前触发的第二次提交（例如代码连续调用两次 `requestSubmit()`，或者处理函数先 `await` 了一个检查，再设置 submitting），读到的还是旧快照里的 `submitting === false`。用户真的连点两次时，两次点击之间 React 通常已经渲染完，按钮已经禁用。

```jsx title="ref 挡住重复调用，state 负责显示"
const submittingRef = useRef(false);
const [submitting, setSubmitting] = useState(false);

async function handleSubmit(e) {
  e.preventDefault();
  if (submittingRef.current) return;  // ref 立刻生效，挡住第二次
  submittingRef.current = true;
  setSubmitting(true);                // state 给界面用：禁用按钮
  try {
    await api.register(values);
  } finally {
    submittingRef.current = false;
    setSubmitting(false);
  }
}
```

<CallBox kind="tip" label="要点">

前端防重复只能减少问题，不能消除。网络重试、用户刷新后再提交，都会让服务器收到两次。关键操作（下单、付款）要让服务器认得出重复请求：前端生成一个幂等键（idempotency key）随请求发送，服务器对同一个键只处理一次。

</CallBox>

React 19 的 `<form action>` 提供了另一种写法：`isPending` 替你管理“提交中”，但它不会丢弃重复提交。第七节会跑一个例子。

## 七、用 Actions 接管提交

[Actions 那一课](/lessons/react-19)讲过 `<form action={fn}>`、`useActionState` 和 `useFormStatus` 的用法。这里只看它们在表单架构里接管了什么：

- `<form action={fn}>`：提交时 React 在过渡更新里运行 `fn`，参数是 FormData，不需要 `onSubmit` 和 `preventDefault`。
- `useActionState(fn, 初始值)`：返回 `[state, formAction, isPending]`。`fn` 的返回值就是下一个 state，所以字段错误可以直接作为返回值。`isPending` 就是第六节的 submitting。
- `useFormStatus()`：在 `<form>` 内部的子组件里读取 `pending`，提交按钮不用再接收 props。

还有一件事要记住：**Action 结束后，React 会重置表单里的非受控字段**，校验失败时也一样。下面的示例有两个表单，用的是同一个模拟服务器。先预测，再运行。

```jsx play title="Action 表单：失败后输入框还剩什么？"
import { useActionState } from 'react';
import { useFormStatus } from 'react-dom';

const rules = {
  username: (v) => v.length >= 3 || '用户名至少 3 个字符',
  email: (v) => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v) || '邮箱格式不正确',
};
function validate(values) {
  const errors = {};
  for (const key of Object.keys(rules)) {
    const r = rules[key](values[key] ?? '');
    if (r !== true) errors[key] = r;
  }
  return errors;
}

// 模拟服务器：真实项目里这是 Server Function，或一个 fetch 请求
async function signupOnServer(values) {
  await new Promise((r) => setTimeout(r, 600));
  const errors = validate(values); // 服务器再校验一次
  if (Object.keys(errors).length) return { errors };
  return { errors: {}, ok: true };
}

// A：失败时只返回 errors
async function signupA(prev, formData) {
  const values = Object.fromEntries(formData);
  return await signupOnServer(values);
}

// B：失败时把输入的值一起返回
async function signupB(prev, formData) {
  const values = Object.fromEntries(formData);
  return { ...(await signupOnServer(values)), values };
}

function SubmitButton() {
  const { pending } = useFormStatus(); // 必须在 form 内部的组件里调用
  return <button disabled={pending}>{pending ? '提交中…' : '注册'}</button>;
}

function SignupForm({ title, action, keepValues }) {
  const [state, formAction] = useActionState(action, { errors: {}, values: {} });
  const err = state.errors.username;
  return (
    <form action={formAction} style={{ marginBottom: 12 }}>
      <b>{title}</b>{' '}
      <input
        name="username"
        defaultValue={keepValues ? state.values.username : undefined}
        aria-invalid={err ? true : undefined}
      />{' '}
      <SubmitButton />
      {err && <small style={{ color: '#c0392b' }}> {err}</small>}
      {state.ok && <small> 注册成功</small>}
    </form>
  );
}

export default function App() {
  return (
    <div>
      <SignupForm title="A 只返回错误" action={signupA} />
      <SignupForm title="B 连输入值一起返回" action={signupB} keepValues />
    </div>
  );
}
```

所以用 Action 做表单，失败时要把 values 一起返回，再用 `defaultValue` 填回去。这和受控表单相反：受控表单的值一直在 state 里，不会丢。

第六节说过，防重复提交要靠 ref，因为 state 是快照。Action 把这件事换成另一个问题：**同一个 `useActionState` 的多次提交不会被丢弃，而是排队依次执行**。按钮不禁用，连点就会提交多次。

```jsx play title="Action 排队：连点会提交几次？"
import { useActionState } from 'react';

let running = 0;
let calls = 0;

async function register(prev, formData) {
  const n = ++calls;
  running++;
  console.log('第 ' + n + ' 次 register 开始，同时在途 ' + running + ' 个');
  await new Promise((r) => setTimeout(r, 500));
  running--;
  console.log('第 ' + n + ' 次 register 结束');
  return { count: prev.count + 1 };
}

export default function App() {
  const [state, formAction, isPending] = useActionState(register, { count: 0 });
  return (
    <form action={formAction}>
      <input name="username" defaultValue="anna" />{' '}
      <button>注册（不禁用）</button>
      <p>已完成 {state.count} 次{isPending ? '，处理中…' : ''}</p>
    </form>
  );
}
```

所以按钮仍然要用 `isPending`（或 `useFormStatus` 的 `pending`）禁用。真正防重复靠服务器的幂等键。

Actions 没有替你做的事：错误什么时候显示（它只在提交后返回错误）、异步检查的竞态、多步表单。把 Action 接进真实项目，有两处和本页的模拟不同：

```tsx title="真实项目：Server Function（需要 Next.js 这类框架，实验台不能运行）"
// actions.js
'use server';
export async function signup(prevState, formData) {
  const values = Object.fromEntries(formData);
  const result = signupSchema.safeParse(values);       // 和客户端共用同一份 schema
  if (!result.success) return { values, errors: z.flattenError(result.error).fieldErrors };
  if (await db.user.exists(values.username)) {          // 只有服务器能判断唯一
    return { values, errors: { username: ['用户名已被占用'] } };
  }
  await db.user.create(result.data);
  redirect('/welcome');                                  // 来自 next/navigation
}
```

一处是 `'use server'`：函数在服务器上运行，参数和返回值要能序列化。另一处是成功后的跳转，由框架提供（这里是 Next.js 的 `redirect`）。表单组件仍然是上面那样的 `useActionState` + `useFormStatus`。

<CallBox kind="tip" label="维护 React 18 项目时">

React 18 的 `<form>` 不接受函数作为 `action`，也没有 `useActionState` 和 `useFormStatus`。同样的结构要手写：`onSubmit` 里 `preventDefault`，用 `new FormData(e.currentTarget)` 读值，用 state 保存错误和提交中状态，防重复提交用第六节的 ref。

</CallBox>

<details className="optional">
<summary><span className="opt-tag">选读</span>React Hook Form 为什么快<small>可以先跳过，需要时再展开</small></summary>

React Hook Form 的 `register('email')` 返回 `{ name, ref, onChange, onBlur }`，展开到原生 input 上，这就是第 45 课讲的 prop getter。字段是非受控的，值存在 DOM 和库内部的对象里，打字不触发 React 渲染。

需要显示的东西（某个字段的错误、是否提交中）通过订阅读取。`formState` 是一个 Proxy：组件读了 `formState.errors`，才会在错误变化时重新渲染；没读 `isDirty`，它变化就不渲染。注意粒度是“哪一种状态”，不是“哪一个字段”：任何字段的错误变化，读了 `errors` 的组件都会渲染，而且渲染的是调用 `useForm` 的那个组件。想让一个字段的错误只重新渲染这个字段，把它拆成子组件，在里面用 `useFormState({ control, name: 'email' })`。拆出去的子组件所在的父组件自己不要再读 `formState`，否则父组件一渲染，子组件照样跟着渲染。校验交给 resolver，传入 Zod schema 即可：`useForm({ resolver: zodResolver(schema), mode: 'onTouched' })`。`mode: 'onTouched'` 就是本课第三节推荐的“离开时显示，显示后输入时更新”。

</details>

<details className="optional">
<summary><span className="opt-tag">选读</span>浏览器原生校验<small>可以先跳过，需要时再展开</small></summary>

`required`、`type="email"`、`minLength`、`pattern` 不写 JavaScript 就能校验，还能用 `:user-invalid` CSS 伪类只在用户交互后标红。缺点是：提示气泡的样式和文字无法统一；不同浏览器和读屏软件的表现不一致；跨字段规则和异步规则写不了。常见做法是保留这些属性（移动端键盘会据此切换），在 form 上加 `noValidate` 关掉气泡，由 schema 负责校验和提示。
