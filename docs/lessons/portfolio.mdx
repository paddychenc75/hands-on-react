## 准备环境

建项目、拆文件、代码质量工具和环境变量，在[项目搭建一课](/lessons/engineering)（第 33 课）讲过；构建、部署、CI 和密钥，在[交付一课](/lessons/delivery)（第 34 课）；样式怎么选，在[样式一课](/lessons/styling)（第 9 课）。下面只留最短的命令，细节回去看那几课。

```bash title="项目一、二用 Vite；项目三用 Next.js（命令见 Next.js 一课）"
# 1. 安装 Node.js（用 24 或更新的 LTS 版本），然后检查
node -v

# 2. 用 Vite 创建 React + TypeScript 项目，并带上 ESLint
npm create vite@latest my-app -- --template react-ts --eslint
cd my-app
npm install
npm run dev          # 打开终端里显示的地址，通常是 http://localhost:5173
npm run lint         # ESLint 由项目自带，不依赖编辑器插件
```

`--eslint` 让模板用 ESLint 并配好 `eslint-plugin-react-hooks`。不加这个参数，目前的模板改用 Oxlint，`npm run lint` 跑的是另一个工具。[城市天气应用](/lessons/project-weather)用的是同一条命令，只是模板换成带 React Compiler 的 `react-compiler-ts`；毕业设计想启用 React Compiler，也可以换成它。编辑器用 VS Code 这类能显示 TypeScript 报错的即可。

模板的 `package.json` 里只有 `dev`、`build`、`lint`、`preview` 四条命令。验收清单用到的 `npm run typecheck` 和 `npm test` 要自己加：在 `scripts` 里写 `"typecheck": "tsc -b"`、`"test": "vitest run"`（Vitest 的安装见[城市天气应用](/lessons/project-weather)的里程碑 0；项目三用 Next.js，类型检查写成 `"typecheck": "tsc --noEmit"`）。

## 项目一：个人记账本（Vite + TypeScript）

预计工时：约 8–12 小时。

| 要求 | 用到的知识 |
|---|---|
| 记录收入和支出，包含金额、分类、日期、备注 | 受控表单（第 8 课）、TypeScript 类型（第 35 课） |
| 按月份筛选，显示收支合计和各分类占比 | 派生数据（第 10 课）、列表渲染（第 7 课） |
| 数据保存在 localStorage，刷新不丢失 | 自定义 Hook（第 16 课） |
| 支持编辑和删除，删除前有确认 | 状态提升（第 11 课）、条件渲染（第 6 课） |
| 为核心计算函数和一个表单写测试 | Vitest + Testing Library（第 38 课） |

## 项目二：电影搜索与收藏（React Router + TanStack Query）

预计工时：约 15–25 小时。接入真实 API 和调试缓存最花时间。

第 40 课的《实战四：城市天气应用》是这个项目的缩小版（同样是搜索、详情、缓存、收藏）。先做完它，再回来做项目二，会顺利很多。

| 要求 | 用到的知识 |
|---|---|
| 接入一个公开 API（如 TMDB）搜索电影，带防抖 | 异步搜索、竞态、防抖（第 17 课的“深入一点”） |
| 列表页、详情页 `/movie/:id`、收藏页三个路由；搜索词放在 URL 里 | React Router（第 36 课） |
| 用 useQuery 获取数据，切换页面后返回时秒开 | TanStack Query（第 37 课） |
| 收藏列表用 Zustand 管理并持久化 | [状态架构](/lessons/state-architecture)（第 28 课）里的 Zustand 部分 |
| 上线版本通过一个 serverless 函数代理 TMDB 请求，前端代码里没有密钥 | 本节“常见坑” |
| 详情页懒加载，图片列表滚动流畅 | lazy 与 Suspense（第 24 课）、性能优化（第 21 课）、虚拟列表（第 25 课） |

<CallBox kind="warn" label="常见坑">

`VITE_` 开头的环境变量会被打包进前端代码，任何人都能看到。只放本来就公开的值，例如接口的基础地址。TMDB 的密钥和令牌绑定你的账号，不算公开值：练习阶段可以先放在 `VITE_` 变量里跑通，上线前要改成由服务端代理或 serverless 函数转发请求，密钥只存在服务端。

</CallBox>

## 项目三：团队任务看板（Next.js 全栈）

预计工时：约 25–40 小时。鉴权、数据库和部署第一次做都要花时间。

第 32 课的《实战：给看板加上 Actions、乐观更新与无障碍》是这个项目前端部分的缩小版（同样是看板，同样要处理等待和失败）。先做完它，再回来做项目三。

| 要求 | 用到的知识 |
|---|---|
| 登录注册，每个用户只能看到自己团队的数据。用成熟的鉴权库（如 Better Auth）或托管的认证服务（如 Clerk），不要自己存密码 | 权限校验（第 39 课）：每个 Server Function 和每次服务端读数据，都要检查用户身份 |
| 看板数据存数据库（如 PostgreSQL + Prisma），在服务端组件中读取 | Server Components（第 30、39 课） |
| 拖动或点击移动卡片时立即生效，失败自动回滚并提示用户 | useOptimistic（第 29 课）、reducer（第 12 课） |
| 部署到 Vercel 等平台，拥有一个可以分享的网址；推送代码后 GitHub Actions 自动检查 | [交付](/lessons/delivery)（第 34 课）：部署、路由回退、CI |

## 加分项：把第六阶段用进项目

三个项目都能用到第六阶段的内容。每个项目至少挑两项做进去，并在 README 里写清楚你的取舍。每一项分两档：**合格**是最低要求，**良好**是做得更完整。两档的标准都是能在页面、网络面板或测试结果里看到的。

| 加分项 | 适合的项目 | 用到的知识 | 合格 | 良好 |
|---|---|---|---|---|
| 详情页用 Suspense 读取数据，没有请求瀑布；切换电影时保留旧内容 | 项目二 | Suspense 数据获取与资源模式（第 42 课） | 有加载中的占位；Network 面板里，详情页需要的请求同时发出，不是一个等一个 | 切换电影时用 `startTransition` 或 `useDeferredValue`，旧内容留在屏幕上，不闪回占位 |
| 服务端渲染没有水合不匹配警告；慢数据放进 Suspense 流式输出 | 项目三 | 流式 SSR、选择性水合与 RSC 缓存（第 43 课） | 控制台没有水合不匹配警告 | 把网速节流到慢速后，页面主体先显示，慢数据所在的区域稍后补上，主体不用等它 |
| 看板数据规范化存储，支持撤销和重做 | 项目三 | 大型应用状态架构实战（第 44 课） | 数据按 id 存放（对象加 id 列表），移动一张卡片只改一处；能撤销上一步 | 能连续撤销、重做多步；做了新操作后重做记录被清空；撤销重做有测试 |
| 封装一个 headless 下拉选择组件，键盘可操作，受控和非受控都支持 | 任意项目 | 组件库 API 设计：Headless 组件（第 45 课） | 只用键盘（上下方向键、Enter、Esc）能选择；元素有 `combobox` 或 `listbox` 的角色，`aria-expanded` 随开合变化 | 受控和非受控两种用法各有一个测试；原生属性和 `ref` 能透传 |
| 表单用一份 schema 在前后端共用；异步校验没有竞态；提交中不能重复提交 | 项目一、项目三 | 表单与校验架构（第 46 课） | 前后端 import 的是同一份 schema；非法输入在两边都被拒绝 | 快速双击提交按钮，只发出一次请求；异步校验（例如用户名是否重复）快速连续输入时，显示的是最后一次输入的结果 |
| 每个面板有可重置的错误边界；错误上报带组件栈和版本号 | 项目二、项目三 | 错误处理与监控（第 47 课） | 一个面板抛错时，其余面板照常显示；点“重置”后这个面板恢复 | 上报请求的内容里能看到组件栈和应用版本号；接住的错误和没接住的错误分别上报 |
| 给最常用的交互定一个性能预算，用 Profiler 记录优化前后的提交次数 | 任意项目 | 性能诊断实战（第 48 课） | README 里写出一条预算，并附优化前后各一张 Profiler 的截图或数字 | 预算用测试守住（例如用 `Profiler` 的 `onRender` 计提交次数并断言上限）；优化后的提交次数不超过优化前的一半 |

## 验收清单：什么时候算“做完了”？

每个项目上线前，按下表逐条操作。**看到“合格”列的结果，这一条才算通过**，不凭感觉打勾。“良好”列是更完整的做法，标准同样是看得见的。

| 类别 | 怎样操作 | 合格 | 良好 |
|---|---|---|---|
| 功能 | 按需求表逐条操作一遍。同时打开浏览器控制台 | 每条需求都能完成；控制台没有红色报错，也没有 key 警告 | 控制台没有任何警告；输入空值、很长的文字和特殊字符，页面也不出错 |
| 数据保存 | 添加几条数据，然后刷新页面 | 数据还在（项目一存在 localStorage，项目三存在数据库） | 手动把存储里的值改成非法内容（项目三：关掉数据库），页面显示错误提示或空状态，不是白屏 |
| 出错 | 在 DevTools 的 Network 面板选 Offline，再执行一次需要请求的操作 | 页面显示错误提示和“重试”按钮。恢复网络后点重试，操作成功 | 出错时已显示的旧数据不会被清空；同一个错误只提示一次 |
| 加载 | 在 Network 面板的节流选项里选 3G（或最慢的一档），刷新页面 | 先显示加载中界面，而不是空白 | 加载中的占位和最终内容大小相近，数据到达时页面没有整体下移；Lighthouse 的累计布局偏移（CLS）不超过 0.1 |
| 空数据 | 搜索一个不存在的词；或清空所有数据 | 显示“没有找到”“还没有记录”这类提示，而不是一片空白 | 提示里带下一步动作，例如“添加第一笔”按钮或换词的建议 |
| 竞态 | 在搜索框里快速连续输入 5 个字 | 最后显示的是最后一个词的结果，不会被旧结果覆盖 | Network 面板里，前面的请求被取消（状态是 canceled）或根本没发出，请求总数少于 5 个 |
| 状态设计 | 打开 React DevTools 的 Components 面板，逐个看 state | 找不到能由其他 state 算出来的 state，例如“合计”“筛选后的列表” | README 里为每份主要状态写一句话：它属于 URL、界面、服务器还是浏览器本地，为什么放在那里 |
| URL | 把带搜索词或页码的链接复制到新标签页打开 | 看到同样的结果 | 浏览器的后退和前进也能还原搜索词和结果；线上直接刷新详情页不是 404 |
| 性能 | 用 React DevTools Profiler 录制一次输入 | 和输入无关的大组件没有跟着重新渲染 | 优化前后各录一次，README 里写出两个提交次数，优化后更少 |
| 无障碍：键盘 | 拔掉鼠标，只用 Tab、Shift+Tab、Enter、空格、Esc 完成核心流程 | 每一步都能完成，并且能看见焦点在哪里；弹窗关闭后焦点回到打开它的按钮 | 焦点顺序和视觉顺序一致；弹窗打开时 Tab 不会跑到弹窗背后；Esc 能关闭弹窗 |
| 无障碍：检查 | 运行 Lighthouse 的“无障碍”检查 | 得分 ≥ 90 | 得分 100，并且用屏幕阅读器（VoiceOver 或 NVDA）能读出核心按钮的名字 |
| 测试 | 运行 `npm test`；再按下一节“自我检验”故意改坏一处 | 全部通过；改坏后至少一个测试变红，改回后全绿 | 至少 3 个核心流程的测试，其中一个是接口返回 500 的错误分支；元素用 role 和 label 查找，没有 `getByTestId` |
| 交付：CI | 推送代码到 GitHub | GitHub Actions 自动运行类型检查（`npm run typecheck`）、lint 和测试，全部通过 | 构建（`npm run build`）也在工作流里；仓库设置了“合并前必须通过检查” |
| 交付：版本 | 检查项目的 React 版本 | 项目使用 React 19 或更新版本，并至少用到一个表单 Action（useActionState） | 表单提交中按钮被禁用并显示“提交中”，失败时有错误提示 |
| 交付：手机 | 用手机打开线上网址 | 页面能正常使用，没有横向滚动条 | 在 360 像素宽的设备模拟下，可点击元素至少 24×24 CSS 像素（WCAG 2.2 的最低要求） |
| 交付：README | 打开 README | 有截图、线上链接、三个设计取舍，以及“最难的问题和解决方法” | 每个取舍写成“选了什么、放弃了什么、为什么”，并写出“如果重做，我会改什么” |

## 自我检验：给核心流程写 3 个测试

验收清单里的“测试”一条，按下面的步骤完成。方法和第 38 课的练习相同：好测试要能抓住 bug。

<CallBox kind="tip" label="步骤">

1. 选出 3 个核心流程。例如记账本：添加一笔支出后合计更新；删除时点“取消”，数据还在；切换月份后只显示这个月的记录。
2. 每个流程写一个测试：`render` → 用 `userEvent` 操作 → 断言用户看到的**确切**结果，例如金额、条数。用 `getByRole` 和 `getByLabelText` 找元素。
3. 故意改坏一处代码，例如合计少加一项，或删除时不弹确认。运行测试：至少一个应该变红。
4. 如果全是绿的，说明断言不够具体。回到第 2 步，把断言改成确切的值。
5. 有网络请求的流程，再用 MSW 让接口返回 500，测试错误提示会出现。

</CallBox>

```jsx title="项目一的第一个测试可以这样写"
it('添加一笔支出后，本月合计增加', async () => {
  const user = userEvent.setup();
  render(<App />);
  await user.type(screen.getByLabelText('金额'), '25');
  await user.click(screen.getByRole('button', { name: '记一笔' }));
  // 断言确切的金额：如果合计少加了一项，这一行会失败
  expect(screen.getByText('本月支出：¥25.00')).toBeInTheDocument();
});
```

## 审查 AI 生成的代码

写代码时你很可能会用 AI 生成初稿。生成的 React 代码要像审查同事的代码一样逐项检查：

- effect 的依赖数组是否完整，清理函数是否存在。
- 列表的 key 是否稳定，不是下标或随机数。
- 有没有把能算出来的值存进 state（派生 state）。
- 表单控件和按钮是否有无障碍标签，能否只用键盘操作。
- memo、useMemo、useCallback 是否真的需要，有没有用 Profiler 的数字支持。

多语言（国际化）不在本课程范围。有这个需求的项目，可以查 react-i18next 或 FormatJS 的文档。

## 把作品变成面试素材

- 每个项目准备 2 分钟讲解：解决什么问题；一个关键的设计取舍；如果重做，你会改什么。
- 能现场写出三个小组件：带防抖的搜索；键盘能操作、读屏软件能读出的标签页；带 reducer 的表单。先回到对应的课，不看答案重写一遍。
- 给一个开源 React 项目提 1 个文档或测试相关的 PR。

## 怎样算学到位了？

与其问学了多少 API，不如用下面这些问题检验自己。如果都能清楚地回答，并且在项目里做到了，你就已经超过了大多数 React 开发者：

- 看到一个 bug，能判断它是渲染问题、状态设计问题，还是 effect 依赖问题
- 能说清楚某个状态为什么放在这里，而不是父组件、Context 或 URL 里
- 页面卡顿时，会先用 Profiler 定位，而不是到处加 useMemo
- 能给团队设计一个好用的公共组件，别人不看文档也能用对
- 读得懂 React 官方文档中的每一个“深入探讨”和“陷阱”小节
- 新特性发布时，能读懂它解决的问题，并判断自己的项目是否需要
