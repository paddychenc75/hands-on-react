到这里，课程能教的已经教完了。最后一步只能靠你自己。**从一个空文件夹开始，做出一个能用、已上线、别人能访问的应用**。下面三个项目难度递增，每一个都对应课程里的一组知识。

本课标的 18 分钟只算阅读。三个项目要在课外完成，预计工时如下（按第一次独立做估算，包含写测试和部署）：

1. 项目一：约 8–12 小时。
2. 项目二：约 15–25 小时。
3. 项目三：约 25–40 小时。

每周投入 5–8 小时，三个项目大约需要 2–3 个月。一次只做一个项目，做完验收清单再开始下一个。

## 准备环境

建项目、拆文件、选样式、管环境变量和部署，都在第 31 课《项目搭建与交付》里讲过。下面只留最短的命令，细节回去看那一课。

```jsx title="项目一、二用 Vite；项目三用 Next.js"
# 1. 安装 Node.js（建议 LTS 版本），然后检查
node -v

# 2. 用 Vite 创建 React + TypeScript 项目
npm create vite@latest my-app -- --template react-ts
cd my-app
npm install
npm run dev          # 打开 http://localhost:5173

# 3. 推荐的编辑器：VS Code + ESLint 插件
```

## 项目一：个人记账本（Vite + TypeScript）

预计工时：约 8–12 小时。

| 要求 | 用到的知识 |
|---|---|
| 记录收入和支出，包含金额、分类、日期、备注 | 受控表单（第 8 课）、TypeScript 类型（第 32 课） |
| 按月份筛选，显示收支合计和各分类占比 | 派生数据（第 9 课）、列表渲染（第 7 课） |
| 数据保存在 localStorage，刷新不丢失 | 自定义 Hook（第 15 课） |
| 支持编辑和删除，删除前有确认 | 状态提升（第 10 课）、条件渲染（第 6 课） |
| 为核心计算函数和一个表单写测试 | Vitest + Testing Library（第 35 课） |

## 项目二：电影搜索与收藏（React Router + TanStack Query）

预计工时：约 15–25 小时。接入真实 API 和调试缓存最花时间。

| 要求 | 用到的知识 |
|---|---|
| 接入一个公开 API（如 TMDB）搜索电影，带防抖 | 异步搜索、竞态、防抖（第 17 课的“深入一点”） |
| 列表页、详情页 `/movie/:id`、收藏页三个路由；搜索词放在 URL 里 | React Router（第 33 课） |
| 用 useQuery 获取数据，切换页面后返回时秒开 | TanStack Query（第 34 课） |
| 收藏列表用 Zustand 管理并持久化 | 状态架构（第 27 课） |
| 上线版本通过一个 serverless 函数代理 TMDB 请求，前端代码里没有密钥 | 本节“常见坑” |
| 详情页懒加载，图片列表滚动流畅 | lazy 与 Suspense（第 22 课）、性能优化（第 20 课）、虚拟列表（第 24 课） |

<CallBox kind="warn" label="常见坑">

`VITE_` 开头的环境变量会被打包进前端代码，任何人都能看到。只放本来就公开的值，例如接口的基础地址。TMDB 的密钥和令牌绑定你的账号，不算公开值：练习阶段可以先放在 `VITE_` 变量里跑通，上线前要改成由服务端代理或 serverless 函数转发请求，密钥只存在服务端。

</CallBox>

## 项目三：团队任务看板（Next.js 全栈）

预计工时：约 25–40 小时。鉴权、数据库和部署第一次做都要花时间。

| 要求 | 用到的知识 |
|---|---|
| 登录注册，每个用户只能看到自己团队的数据。用成熟的鉴权库（如 Better Auth）或托管的认证服务（如 Clerk），不要自己存密码 | 权限校验（第 36 课）：每个 Server Function 和每次服务端读数据，都要检查用户身份 |
| 看板数据存数据库（如 PostgreSQL + Prisma），在服务端组件中读取 | Server Components（第 29、36 课） |
| 拖动或点击移动卡片时立即生效，失败自动回滚并提示用户 | useOptimistic（第 28 课）、reducer（第 11 课） |
| 部署到 Vercel 等平台，拥有一个可以分享的网址；推送代码后 GitHub Actions 自动检查 | 项目搭建与交付（第 31 课）：部署、路由回退、CI |

## 加分项：把第六阶段用进项目

三个项目都能用到第六阶段的内容。每个项目至少挑两项做进去，并在 README 里写清楚你的取舍。

| 加分项 | 适合的项目 | 用到的知识 |
|---|---|---|
| 详情页用 Suspense 读取数据，没有请求瀑布；切换电影时保留旧内容 | 项目二 | Suspense 数据获取与资源模式（第 39 课） |
| 服务端渲染没有水合不匹配警告；慢数据放进 Suspense 流式输出 | 项目三 | 流式 SSR、选择性水合与 RSC 缓存（第 40 课） |
| 看板数据规范化存储，支持撤销和重做 | 项目三 | 大型应用状态架构实战（第 41 课） |
| 封装一个 headless 下拉选择组件，键盘可操作，受控和非受控都支持 | 任意项目 | 组件库 API 设计：Headless 组件（第 42 课） |
| 表单用一份 schema 在前后端共用；异步校验没有竞态；提交中不能重复提交 | 项目一、项目三 | 表单与校验架构（第 43 课） |
| 每个面板有可重置的错误边界；错误上报带组件栈和版本号 | 项目二、项目三 | 错误处理与监控（第 44 课） |
| 给最常用的交互定一个性能预算，用 Profiler 记录优化前后的提交次数 | 任意项目 | 性能诊断实战（第 45 课） |

## 验收清单：什么时候算“做完了”？

每个项目上线前，按下表逐条操作。<strong>看到“应该看到”的结果，才算这一条通过。</strong>不凭感觉打勾。

| 类别 | 怎样操作 | 应该看到 |
|---|---|---|
| 功能 | 按需求表逐条操作一遍。同时打开浏览器控制台 | 每条需求都能完成；控制台没有红色报错，也没有 key 警告 |
| 功能 | 添加几条数据，然后刷新页面 | 数据还在（项目一存在 localStorage，项目三存在数据库） |
| 出错 | 在 DevTools 的 Network 面板选 Offline，再执行一次需要请求的操作 | 页面显示错误提示和“重试”按钮。恢复网络后点重试，操作成功 |
| 加载 | 在 Network 面板的节流选项里选 3G（或最慢的一档），刷新页面 | 先显示加载中界面，而不是空白；数据到达时布局不跳动 |
| 空数据 | 搜索一个不存在的词；或清空所有数据 | 显示“没有找到”“还没有记录”这类提示，而不是一片空白 |
| 竞态 | 在搜索框里快速连续输入 5 个字 | 最后显示的是最后一个词的结果，不会被旧结果覆盖 |
| 状态设计 | 打开 React DevTools 的 Components 面板，逐个看 state | 找不到能由其他 state 算出来的 state，例如“合计”“筛选后的列表” |
| URL | 把带搜索词或页码的链接复制到新标签页打开 | 看到同样的结果 |
| 性能 | 用 React DevTools Profiler 录制一次输入 | 和输入无关的大组件没有跟着重新渲染 |
| 无障碍 | 拔掉鼠标，只用 Tab、Shift+Tab、Enter、空格、Esc 完成核心流程 | 每一步都能完成，并且能看见焦点在哪里；弹窗关闭后焦点回到打开它的按钮 |
| 无障碍 | 运行 Lighthouse 的“无障碍”检查 | 得分 ≥ 90 |
| 测试 | 运行 `npm test`；再按下一节“自我检验”故意改坏一处 | 全部通过；改坏后至少一个测试变红，改回后全绿 |
| 交付 | 推送代码到 GitHub | GitHub Actions 自动运行 `tsc --noEmit`、ESLint 和测试，全部通过 |
| 交付 | 检查项目的 React 版本 | 项目使用 React 19 或更新版本，并至少用到一个表单 Action（useActionState） |
| 交付 | 用手机打开线上网址 | 页面能正常使用，没有横向滚动条 |
| 交付 | 打开 README | 有截图、线上链接、三个设计取舍，以及“最难的问题和解决方法” |

## 自我检验：给核心流程写 3 个测试

验收清单里的“测试”一条，按下面的步骤完成。方法和第 35 课的练习相同：好测试要能抓住 bug。

<CallBox kind="tip" label="步骤">

1. 选出 3 个核心流程。例如记账本：添加一笔支出后合计更新；删除时点“取消”，数据还在；切换月份后只显示这个月的记录。
2. 每个流程写一个测试：`render` → 用 `userEvent` 操作 → 断言用户看到的**确切**结果，例如金额、条数。用 `getByRole` 和 `getByLabelText` 找元素。
3. 故意改坏一处代码，例如合计少加一项，或删除时不弹确认。运行测试：至少一个应该变红。
4. 如果全是绿的，说明断言不够具体。回到第 2 步，把断言改成确切的值。
5. 有网络请求的流程，再用 MSW 让接口返回 500，测试错误提示会出现。

</CallBox>

```jsx title="项目一的第一个测试可以这样写"
it('添加一笔支出后，本月合计增加', async () => {
  const user = userEvent.setup();
  render(<App />);
  await user.type(screen.getByLabelText('金额'), '25');
  await user.click(screen.getByRole('button', { name: '记一笔' }));
  // 断言确切的金额：如果合计少加了一项，这一行会失败
  expect(screen.getByText('本月支出：¥25.00')).toBeInTheDocument();
});
```

## 审查 AI 生成的代码

写代码时你很可能会用 AI 生成初稿。生成的 React 代码要像审查同事的代码一样逐项检查：

- effect 的依赖数组是否完整，清理函数是否存在。
- 列表的 key 是否稳定，不是下标或随机数。
- 有没有把能算出来的值存进 state（派生 state）。
- 表单控件和按钮是否有无障碍标签，能否只用键盘操作。
- memo、useMemo、useCallback 是否真的需要，有没有用 Profiler 的数字支持。

多语言（国际化）不在本课程范围。有这个需求的项目，可以查 react-i18next 或 FormatJS 的文档。

## 把作品变成面试素材

- 每个项目准备 2 分钟讲解：解决什么问题；一个关键的设计取舍；如果重做，你会改什么。
- 能现场写出三个小组件：带防抖的搜索；键盘能操作、读屏软件能读出的标签页；带 reducer 的表单。先回到对应的课，不看答案重写一遍。
- 给一个开源 React 项目提 1 个文档或测试相关的 PR。

## 怎样算学到位了？

与其问学了多少 API，不如用下面这些问题检验自己。如果都能清楚地回答，并且在项目里做到了，你就已经超过了大多数 React 开发者：

- 看到一个 bug，能判断它是渲染问题、状态设计问题，还是 effect 依赖问题
- 能说清楚某个状态为什么放在这里，而不是父组件、Context 或 URL 里
- 页面卡顿时，会先用 Profiler 定位，而不是到处加 useMemo
- 能给团队设计一个好用的公共组件，别人不看文档也能用对
- 读得懂 React 官方文档中的每一个“深入探讨”和“陷阱”小节
- 新特性发布时，能读懂它解决的问题，并判断自己的项目是否需要
